# CCKIT_CONTROLLER — фазовые контракты

**Проект:** пульт над набором `claude-agent-kit`
**Состояние набора:** живой источник — файл `.claude/VERSION` и строка `node .claude/hooks/banner.mjs --compact` (версия и отпечаток вместе). Числа здесь не дублируются: снимок в тексте устаревает молча.
**Целевая версия пульта:** 1.0.0
**Формат:** обзор + шесть фазовых контрактов, каждый выполняется отдельным прогоном конвейера

Макет интерфейса — `cckit-controller-ui/`. **Этот документ — единственный источник по
пульту:** концепция, границы и фазы собраны здесь. Отдельного файла концепции больше нет.

Карта набора — `CCKIT_UPGRADE.md`. Их связь: фаза 5 набора (`DONE.md` и асинхронная
приёмка) — предусловие фазы 2 пульта. Фазу 1 (демон) можно делать параллельно, она
от набора не зависит.

---

## Что это

**Своя ADE — среда для работы с агентами, а не с кодом.**

Сегодня рабочее место выглядит так: VS Code открыт ради одной панели Claude Code, три
проекта — три окна, состояние конвейера читается открыванием `STATE.md` руками, карта
памяти запускается командой и открывается в браузере, статистика печатается в чат,
окно приёмки живёт в консоли и глючит. Код при этом не правится вообще.

Пульт собирает это в одно окно: сессии всех проектов, задачи со статусами, диффы,
память, метрики, установка набора в проект — и доступ с телефона.

**Чем это не является.** Не редактором кода. Не заменой Claude Code — он его запускает.
Не облачным сервисом.

**Распространение.** Пользователь скачивает пульт; набор едет внутри него и ставится
в проекты по кнопке. Работа без пульта остаётся возможной, но перестаёт быть основным
способом.

## OVERVIEW

### Три правила, из которых следует всё остальное

**1. Истина живёт в `.claude/` внутри проекта.** Пульт — витрина и пускатель. Он ничего
не хранит о проекте у себя: версию, отпечаток, задачи, настройки — вычитывает при каждом
обращении. Своё у пульта только реестр путей и собственные настройки.

**2. Кит обязан работать без пульта.** Ни одна фаза не имеет права добавить в набор
зависимость от контроллера. Если пульт не запущен — конвейер работает как работал.

**3. Пульт не снимает `[СТОП]`.** Он делает ответ на него быстрым, а не необязательным.
Машинный гейт остаётся внутри хода агента и пульту не подчиняется.

### Порядок фаз

```
Фаза 0  Журнал событий в ките (events.jsonl)      → без него нет дашборда
Фаза 1  Демон: реестр, чтение, HTTP API           → фундамент
Фаза 2  Рабочее место: терминал, просмотр, задачи → первый срез, остановка снята
Фаза 3  Оболочка: окно, трей, диалог папки        → нативное
Фаза 4  Действия: развернуть, ответить, настроить → пульт начинает писать
Фаза 5  Удалённый доступ: VPS, PWA, уведомления
Фаза 6  Память, карта, дашборд                    → требует фазы 0
```

**Почему терминал стоит вторым, а не пятым.** Владелец не правит код руками — он
взаимодействует с агентами, а VS Code служит ему оболочкой для запуска Claude Code
и просмотра диффов. Значит первый срез обязан заменить VS Code, иначе им не станут
пользоваться и обратной связи не будет. Пульт без терминала — приборная панель рядом
с рабочим местом; пульт с терминалом — само рабочее место.

Следствие, которое надо принять сознательно: **правило «кит работает без пульта»
из страховки превращается в дисциплину.** Пульт сломался — конвейер обязан
запускаться из системной консоли. Это проверяется в критерии готовности каждой фазы,
а не подразумевается.

**После фазы 2 обязательная остановка** — две недели пользоваться тем, что вышло,
прежде чем писать дальше. Макет покрывает всё до фазы 5, и это его главная опасность:
он тянет строить целиком.

> **Остановка ОТМЕНЕНА 02.09.2026 решением человека.** Фаза 3 планируется по действующему
> контракту, а не по двум неделям записей. Взамен принято условие **«полнота важнее
> отделки»**: каждый экран обязан быть и работать, шероховатости принимаются, а бэклог
> проблем человек собирает, работая в готовом пульте. Опасность макета этим решением
> не снимается — она снимается порядком фаз 3 → 4 → 6 тремя отдельными задачами.
> Подробнее — §2.7, там же прежний текст остаётся буквой фазы 2.

### Что НЕ входит

- **Редактор кода.** Пульт не заменяет VS Code и не пытается.
- **Своё хранилище состояния проектов.** Ни базы, ни кэша артефактов. Реестр путей —
  единственное, что пульт помнит.
- **Облако и многопользовательский режим.** Демон слушает локальную сеть. Всё, что
  сложнее — отдельный продукт с другой моделью угроз.
- **Управление скиллами и агентами.** В макете эти вкладки нарисованы, но механизмов
  в ките нет. До появления — не реализовывать.
- **Автоматическая правка чужих файлов проекта.** Пульт пишет только в `.claude/`
  и только то, что перечислено в контракте фазы.

## PHASE_00_EVENTS — журнал событий в ките

> **Зачем.** Кит производит прозу: `PLAN.md`, `REVIEW.md`, `SECURITY.md`. Машинного в нём
> два файла, и оба снимки — `GATE_STATE.json` и `VERIFY.json` перезаписываются каждым
> прогоном. Журнал в `STATE.md` человекочитаемый, на одну задачу, между задачами
> не сводится. Значит статистику собирать не из чего, и никакая красота интерфейса
> этого не исправит.
>
> **Это работа по киту, а не по пульту.** Она полезна сама по себе — из журнала растут
> ретроспектива и ответ на вопрос «где мы тратим время», даже если пульт никогда
> не будет написан.

### 0.1. Файл

```
.claude/artifacts/events.jsonl      # дописывание строкой, никогда не перезапись
```

Одна строка — одно событие:

```json
{"ts":"2026-08-28T09:14:22.031Z","task_id":"2026-08-28-...","event":"status_changed","payload":{"from":"planning","to":"implementing"}}
```

Поля: `ts` (ISO 8601, UTC), `task_id`, `event`, `payload`. Ничего больше.

### 0.2. Кто пишет

Пишут **три** места, и все три — хуки кита, не агенты:

- `task.mjs` — `task_opened`, `status_changed`, `task_closed`;
- `gate.mjs` — `gate_armed`, `gate_result`;
- `session.mjs` — `session_started`, `session_ended`.

Семь имён, и они обязаны совпадать с белым списком `EVENTS` в `.claude/hooks/events.mjs:49`
**посимвольно**. Расхождение бьёт в обе стороны: имя вне списка хук молча не запишет, а имя
в списке без пишущего делает «события не было» неотличимым от «событие не логируется». Имя
заводится только вместе с кодом, который его пишет, и в том же заходе.

**`gate_blocked` не заводится** — это решение, а не пропуск. Оба исхода блокировки (три
красных прогона подряд и подмена набора проверок между взводом и концом хода) уже различимы
внутри `gate_result` по `payload.status` со значением `blocked` и уточняющей паре: `attempt`
для первого случая, `reason: checks-changed` для второго. Третье имя нового знания не даёт,
а группировку усложняет — «сколько ходов кончилось блокировкой» пришлось бы считать по двум
именам вместо одного.

Отдельного логирования агенты не делают. Ручная запись произвольного текста требует
подтверждения человека и в `allow` не входит — намеренно.

**Отсутствие события — не вердикт.** Пропуск в журнале читается как «неизвестно» и никогда
как «приёмка прошла», «проверок нет» или «работы не было». Вердикт сверяется со `STATE.md`
задачи и `VERIFY.json`; журнал — рубеж видимости, а не доказательство. Причина не
теоретическая: в этом репозитории 2026-08-29 хуки не вызывались средой вовсе — сессия была
запущена с рабочим каталогом `<репозиторий>/.claude`, то есть проектом Claude Code считал
саму папку `.claude` и настройки искал в `.claude/.claude/settings.json`, которого нет.
Ни `SessionStart`, ни `PostToolUse`, ни `Stop` при этом не зарегистрированы, и журнал молчал
о взведённом гейте целый день. Это ограничение среды, а не кита, и починить его изнутри
набора нельзя — но статистика фазы 5 обязана уметь отвечать «данных нет» вместо того, чтобы
достраивать их до удобного ответа.

**Транскрипт сессии — тоже не вердикт, и по двум причинам.** Разбор окна 2026-08-30
10:02:00–10:04:17 UTC (три перезапуска: пять концов, два старта, три разных `session_id`
среди концов) дал две находки, обе про среду, а не про кит. Первая: у сессии может **вовсе
не быть файла транскрипта** — для `377c737b` и `7b01eb01` в каталогах проектов Claude Code
нет ни одного файла, хотя среда завела им каталоги окружения (10:03:24.611Z и 10:04:13.655Z)
и позвала `SessionEnd`: обе записи `session_ended` в журнале есть. Вторая: **успешный хук,
который ничего не печатает, записи в транскрипте не оставляет**. Доказательство прямое —
2026-08-29T23:33:00.936Z в транскрипте лежит `hook_success | SessionStart:resume |
banner.mjs --compact | 111ms` и ни одной записи про `session.mjs --start`, а в журнале
строка `session_started` от 23:33:00.951Z: старт отработал. Значит «в транскрипте нет записи
`SessionStart`» **не означает** «хук не звали»: в транскрипт попадают отменённые хуки
и успешные с выводом, молчаливые успешные — нет. Отсутствие записи о хуке читается так же,
как отсутствие события в журнале, — «неизвестно».

**Что по этому окну осталось открытым.** Для `377c737b` (конец 10:03:42.227Z) отличить
«среда не звала `SessionStart`» от «звала, а хук не отработал» **нечем**: транскрипта нет,
а молчаливый успех следа не оставляет. Объяснение «сессия старше регистрации хуков»
отпадает — регистрация появилась в настройках вечером 2026-08-29, сессия открыта утром
2026-08-30. Это записано открытым вопросом, а не версией. Для `7b01eb01` (конец
10:04:16.995Z) в журнале есть старт через 0,43 с после появления каталога окружения
(10:04:14.081Z), но это соседство во времени — ровно тот способ сопоставления, который
§0.3 отменяет; строгой пары не выходит. Такие случаи и закрывает идентификатор в payload
старта: с ним вопрос «чей это конец» перестаёт быть вопросом.

**Что имеет право попасть в payload.** Только значения из закрытого словаря или прошедшие
регулярку. Не попадает **никогда**: свободный текст человека, промты и их фрагменты,
абсолютные пути, имена пользователя и машины, содержимое разбираемых файлов, сообщения
об ошибках. От сообщений об ошибках — отдельно: в payload идёт только код или имя класса
(`e.code || e.name`), потому что `e.message` в современном Node цитирует разбираемое
содержимое, а `GATE_STATE.json` хранит заголовок задачи — то есть текст человека уехал бы
в журнал через сообщение об ошибке, мимо этого правила. Полный текст остаётся в stderr,
где он и нужен человеку. Единственное унаследованное исключение — `task_opened.payload.title`:
заголовок задачи, свободный текст по своей природе. Он проходит ту же очистку, что все
значения, но `<`, `>` и `&` она не трогает — **фаза 5 обязана экранировать при выводе**,
иначе первый же заголовок с угловой скобкой станет разметкой в дашборде.

### 0.3. Границы события

`session_started` и `session_ended` **нужны**: без них нельзя отличить «задача заняла
три часа» от «задачу открыли утром, закрыли вечером, работали сорок минут». Пишет
`session.mjs` с хуков `SessionStart` и `SessionEnd`. В payload обоих — `session_id`;
рядом с ним у старта `source`, у конца `reason`.

**Границы сопоставляются по `session_id`, а не по соседству во времени.** Прежнее правило
(«сопоставить старт со следующим по времени концом») отменено наблюдением: **сессии
перекрываются во времени**. Окно 2026-08-30 10:02:00–10:04:17 UTC, три перезапуска: пять
записей `session_ended`, две `session_started`, и среди концов **три разных** `session_id`
(`275c73b1` трижды, `377c737b`, `7b01eb01`). При перекрытии «следующий конец» принадлежит
другой сессии, и пара по соседству оказывается ложной.

**При этом `session_id` не уникален** — второе обстоятельство, и оно никуда не делось. Мост
VS Code при перезапуске редактора переподключается к той же сессии, сохраняя идентификатор
и файл транскрипта, поэтому два перезапуска подряд дают две записи `session_ended` с одним
и тем же `session_id` — в журнале это зафиксировано (18:15:36Z и 18:16:18Z, разница
42 секунды). Разбор обязан быть верным при **обоих** обстоятельствах сразу, отсюда правило
и два прежних запрета, которые остаются в силе как следствия неуникальности:

- **сопоставлять внутри одного `session_id`, по порядку**: события с равным идентификатором
  выстраиваются по времени, и k-й старт закрывается k-м концом того же id — не «первый
  со всеми» и не «все в одну сессию»;
- **не дедуплицировать по `session_id`** — склеятся разные реальные границы, и время
  между ними пропадёт из подсчёта;
- **не считать сессии как `distinct session_id`** — счёт окажется заниженным.

**Непарная запись — норма, а не сбой.** Конец без старта и старт без конца дают сессию
неизвестной длительности: в средние она не входит, и ближайший чужой старт или конец ей
**не приписывается**. Так же читается и §0.2: отсутствие события — «неизвестно», а не вердикт.
Откуда они берутся, разобрано там же: у сессии может не быть транскрипта вовсе, среда может
позвать `SessionEnd`, не позвав `SessionStart`, а молчаливый успешный хук следа в транскрипте
не оставляет — то есть даже разбор транскрипта не всегда отвечает, звали хук или нет.

**История payload на старте — чтобы отменённое решение не вернулось вслепую.** До 2026-08-30
у `session_started` payload был **пустым**, и это была принятая цена: хук на `SessionStart`
не читал stdin, потому что блокирующее чтение ждало EOF, которого мост на старте не присылает,
и хук погибал по внешнему таймауту, не записав ничего (`hook_cancelled … --start … 10219ms`
против `"timeout": 10`). Цена считалась приемлемой ровно потому, что действовало отменённое
теперь правило «пары по времени». Сейчас `--start` читает stdin **с дедлайном** 500 мс и кладёт
в payload `session_id` и `source`; чтение с дедлайном разбирает то, что успело прийти, и хук
идёт дальше. Худший путь (среда трубу не закрыла, данных нет) стоит полного времени процесса
598 / 603 / 620 мс — замерено на стенде вне репозитория, порог 700 мс был записан до замера.
Событие пишется в обоих случаях: не пришло ничего — payload пуст, но строка есть, и правило
про непарные записи выше это допускает. Подробности и условие, при котором чтение убирают
обратно, — в шапке `session.mjs`.

> **Что подтверждено чем.** Состав payload и цена чтения подтверждены **стендом**: хук
> запускался отдельным процессом с подставленным входом. Что идентификатор на `SessionStart`
> присылает **живая среда**, подтверждается только полным перезапуском Claude Code — это
> наблюдение **ожидается** и здесь не заявлено как выполненное. Если среда до дедлайна ничего
> не присылает, payload старта останется пустым; правило разбора выше от этого не ломается —
> такие записи читаются как непарные.

### Критерий готовности

- [ ] Файл дописывается, не перезаписывается — проверить тремя прогонами подряд
- [ ] Красная приёмка оставляет запись до того, как ход вернётся агенту
- [ ] Запись переживает падение хука — но порядок остаётся «действие → событие», а не наоборот:
      событие обязано отражать случившееся, а не намерение, которое могло не состояться.
      Устойчивость даёт запись из верхнеуровневого `catch` самого хука (`gate.mjs`, `task.mjs`)
- [ ] Агенту закрыта запись правами (`Write`/`Edit` в `deny`), чтение открыто
- [ ] Файл выведен из-под git и не уезжает пользователям

## PHASE_01_DAEMON — демон

> **Зачем.** Нужен один процесс, который знает про все проекты сразу и умеет читать их
> `.claude/`. Всё остальное — надстройки над ним.

### 1.1. Что это

Локальный сервис на Node. Зависимости разрешены — это не кит. Отдаёт HTTP на
`127.0.0.1:7331` и, по настройке, на локальную сеть.

### 1.2. Реестр

```
%APPDATA%\cckit\registry.json      # Windows
~/.config/cckit/registry.json      # POSIX
```

Хранит только: путь к проекту, имя, время последнего просмотра. **Ничего о содержимом
проекта.** Пропавший путь помечается недоступным, но не удаляется автоматически.

### 1.3. Чтение проекта

На каждый запрос — заново с диска:

| Что | Откуда |
|---|---|
| версия | `.claude/VERSION` |
| отпечаток и сверка с эталоном | `kit-fingerprint.mjs`, **не** сравнение номеров версий |
| задачи и статусы | `.claude/tasks/*/STATE.md` |
| артефакты задачи | `PLAN.md`, `SECURITY.md`, `REVIEW.md` в папке задачи |
| состояние гейта | `GATE_STATE.json`, `VERIFY.json` |
| события | `events.jsonl` |
| профиль | `PROJECT_PROFILE.md` |

**Ничего не кэшировать между запросами.** Кэш здесь — это второй источник правды,
то есть ровно та болезнь, от которой в ките завели отпечаток.

### 1.4. Состояния, которые обязаны быть в API

Не только «всё хорошо»:

- путь пропал или недоступен;
- кит в проекте не установлен;
- кит установлен, но старой структуры (до `tasks/<id>/`);
- версия совпала, отпечаток разошёлся;
- `.claude/` есть, но не наш (чужой проект с ручными настройками).

### 1.5. Форма ответа

Поля — как в разделе 7 README макета. Отклонения от него фиксируются здесь, а не
в коде молча.

#### Форма ответа фазы 1

Реализована в `pult/` и является договором с фазой 2. **Перечень ниже — белый список,
а не пример:** поля, которого здесь нет, процесс не покидают ни при каких режимах и ключах;
чужие объекты в ответ не разворачиваются, поля переносятся поимённо.

```
GET /health          -> { ok, pult, node }
GET /projects        -> { generated_at,
                          reference: { path, version,
                                       fingerprint: { value, scan_truncated, reason } },
                          projects: [ ... ],
                          registry_faults: [ { field, code } ],   // только если они есть
                          projects_truncated: true }              // только при обрезке списка
GET /projects/:id    -> то же на один проект + tasks: [ ... ]

Проект   id, name, path
         touched: { registry_seen: {value, kind} | null,
                    kit_changed:   {value, kind, source} | null }
         state: ok | unreachable | no_kit | foreign | legacy
         version: "1.17.0" | null
         fingerprint: { value, reference, verdict: match|mismatch|unknown,
                        diverged[], truncated, scan_truncated, reason }
         profile: filled | template | absent | null
         active_task: {…} | null
         gate: {…} | null
         faults: [ { field, code } ]

Задача   id, title, status, mode, class, branch,
         created: {value, kind: "local-naive"} | null,
         updated: {value, kind: "local-naive"} | null,
         review_iterations, audit_iterations, stop_kind,
         review:   { verdict, critical, important, minor } | null,
         security: { verdict } | null,
         done:     { present, summary, checklist[], date: {value, kind: "date"} | null } | null,
         log: [ {time: {value, kind: "clock"} | null, text} ]

Гейт     task_id, status, attempts, verify,
         armed_at: {value, kind: "utc-iso"} | null,
         verify_report: { status, total, passed, failed_count, failed } | null
```

`generated_at` — собственное время демона (UTC ISO), а не значение из чужого файла.
Каждая строка свободного текста очищена от управляющих символов и обрезана по потолку;
факт обрезки отмечается кодом в `faults[]`.

`registry_faults` и `projects_truncated` — поля верхнего уровня, и в белом списке они стоят
не для красоты: `registry_faults` появляется, когда в реестре пульта нашлись негодные записи
(те же пары «поле, код», что и в `faults[]` проекта), а `projects_truncated` — когда записей
в реестре больше потолка и список проектов обрезан.

**Одинаковые имена — только у одинаковых смыслов.** `scan_truncated` значит «обход неполон»
и у проекта, и у эталона; обрезка СПИСКА ПРОЕКТОВ называется `projects_truncated`; слово
`truncated` осталось ровно за одним смыслом — обрезкой списка расхождений `diverged[]`.
Три разных смысла под одним именем в одном ответе заставили бы потребителя, читающего поле
единообразно, ошибиться на одном из объектов.

#### Отклонения от раздела 7 макета

1. **Отпечаток — объект, а не готовая фраза.** Отдаются значение, эталон, вердикт, список
   расхождений и **два разных признака усечения**: `truncated` (обрезка списка расхождений
   по потолку) и `scan_truncated` (неполный обход состава). Путать их нельзя: первый говорит
   «показано не всё», второй — «посчитано не по всему», и второй всегда даёт `unknown`.
   У эталона признак один и называется он `scan_truncated` — тем же словом и в том же смысле,
   что у проекта.
2. **Признак расхождения заменён парой «состояние проекта + вердикт отпечатка».** Один флаг
   схлопывал четыре разных состояния раздела 1.4 в одно, и по нему нельзя было отличить
   «кита нет» от «отпечаток разошёлся».
3. **У отказа отдаётся только код.** Заголовки, тексты и кнопки — интерфейс фазы 4; API
   отдаёт машинное слово из закрытого словаря, а формулировку выбирает потребитель.
4. **Профиль отдаётся тремя значениями** (`filled`, `template`, `absent`) плюс `null`
   на нечитаемом. Именованных профилей в ките сегодня нет.
5. **Статус задачи отдаётся словом самого кита** — совпадением с закрытым словарём
   из девяти статусов, а не ярлыком макета и не сырой строкой. В ките девять статусов против
   пяти ярлыков макета, а ярлыка «простой» в ките нет вовсе.
6. **Идентификатор задачи имеет форму «дата-слаг»**, а не выдуманную в макете.
7. **Гейт — объект проекта, а не поля задачи.** Приёмка считается по рабочему дереву, дерево
   одно на все задачи, поэтому связь с задачей — только поле `task_id`.
8. **Счётчик заглушек убран:** машинного источника у него нет.
9. **Относительные строки времени заменены двумя разными величинами** — временем последнего
   просмотра (`registry_seen`) и временем последнего изменения кита (`kit_changed`, с полем
   `source`). Раздел 5.1 макета и раздел 1.2 контракта говорят о разном, и склеивать их нельзя.
10. **Готовая русская фраза тревоги не отдаётся.** Текст — дело интерфейса.
11. **Признак «нужно обновить» не отдаётся:** раздел 1.3 прямо запрещает сравнение номеров
    версий как основание.
12. **Форм фаз 2–6 в API фазы 1 нет** и заглушками они не появятся.
13. **Пять состояний отказа раздела 5.2 макета не совпадают с пятью состояниями раздела 1.4
    контракта.** API следует контракту; макет разбирается на фазе 2.

#### Добавления к макету

14. **Список расхождений у отпечатка** (`diverged[]`). Здесь макет точнее контракта, а
    пофайловые хеши демон и так считает — отдать их дешевле, чем заставлять человека искать
    руками.
15. **Пометка вида у каждого времени** (`local-naive`, `utc-iso`, `clock`, `date`).
    Пометка **обещает**, что значение под ней прошло проверку привязанной регуляркой своего
    вида; не совпавшее время отдаётся как `null` с кодом отказа, а не «как есть». Ставит
    пометку единственная функция, руками объект времени не собирает ни один модуль.

#### 16. Оговорка о выводе: три множества, а не общая гарантия

**(1) Проверено машинно** — совпадением с закрытым словарём кита или привязанной регуляркой,
и потому экранирования не требует: версия, идентификаторы задач и проектов, имена событий,
все времена, `status`, `mode`, `class` и `stop_kind` задачи, `status` и `verify` гейта,
вердикты ревью и аудита, счётчики задачи и `attempts` гейта, коды в `faults[]` и `reason`,
`state` проекта, `profile`, `verdict` отпечатка. Не совпало — `null` и код отказа.

**Оговорка к (1): словарь — это снимок кита, а не его импорт.** Пропущенное в снимке живое
значение отказ даёт безопасный (чужая строка наружу не уходит), но «проверено машинно»
превращается в «поле пусто». Так и вышло со статусом гейта: словарь знал два значения
из трёх, и у любого проекта, прошедшего приёмку, `gate.status` уезжал как `null` с кодом
`enum_unrecognised`. Перечень берётся по всем вызовам `writeState()` в `.claude/hooks/gate.mjs`
(`arm()` пишет `implementing`, `decide()` — `verified` и `blocked`), а не по словам,
встречающимся в тексте хука: часть из них — payload события, а не состояние на диске.
Словари сверяются с китом при каждом обновлении набора, там же, где гоняется сторож копии
отпечатка.

**(2) Свободный текст, который экранировать обязан потребитель:** `title` и `branch` задачи,
строки журнала (`log[].text`), `summary` и пункты чек-листа итога, имена упавших проверок
приёмки, `name` и `path` проекта, `reference.path`, пути в списке расхождений `diverged[]`.
Они очищены от управляющих символов и обрезаны по потолку, но `<`, `>` и `&` в них живые:
без экранирования при выводе фаза 2 вставит заголовок задачи в разметку. Это прямое
следствие §0.2 — заголовок задачи пишет человек.

**(3) Поля, у которых машинной проверки нет, и причина, по которой её нет:**

- `branch` — приходит из `gitBranch()` в `.claude/hooks/task.mjs`, а имена веток git почти
  произвольны: закрытого словаря нет и быть не может;
- `name` и `path` проекта — имя каталога на диске задаёт человек, а не кит, поэтому
  проверяется только форма пути (абсолютность, отсутствие нулевого байта и управляющих
  символов, потолок длины), а содержимое произвольно;
- `reference.path` — путь мастер-копии набора в домашнем каталоге, то есть такой же путь
  на диске и с именем пользователя внутри. Он строится демоном (`os.homedir()` плюс два
  постоянных имени), но всё, что можно о нём сказать машинно, — это форма пути: словаря
  у имени домашнего каталога нет. Отсюда и место во множестве (2), рядом с `path` проекта;
- `diverged[]` — имена файлов и каталогов чужого кита; обёртка списка состава отбивает
  абсолютные записи, две точки, обратный слэш и длину, но не набор символов.

Эти поля живут во втором множестве по обязанности потребителя и **в машинных гарантиях API
не участвуют**. Общей гарантии вида «всё прочее безопасно по построению» в разделе
быть не должно: на полях третьего множества она была бы неправдой, а фаза 2 приняла бы
её за разрешение не экранировать.

### Критерий готовности

- [ ] `GET /projects` отдаёт список с версией и результатом сверки отпечатка
- [ ] Удаление проекта с диска не роняет демон — проект помечен недоступным
- [ ] Проект без кита отдаётся с явным признаком, а не пропадает из списка
- [ ] Два запроса подряд читают диск дважды — проверить правкой файла между ними
- [ ] Демон не пишет в `.claude/` ни одного байта на этой фазе

### 2.1. Терминал Claude Code

`node-pty` в демоне → вебсокет → `xterm.js` в интерфейсе. Второй канал: `claude`
в неинтерактивном режиме с потоковым JSON — из него живут структурные панели.

**Следствие про TTY.** Псевдотерминал даёт настоящий TTY, значит `verify.mjs --accept`
из окна пульта работает. Защита сохраняется: она про отсутствие TTY, а не про место
запуска.

**Чем платим.** Терминал в окне — доступ к оболочке на машине.

**Поэтому в фазе 2 демон слушает только петлевой адрес** (решение от 01.09.2026, закрывает
открытый вопрос №2). Локальная сеть не включается вовсе, и телефон переезжает в фазу 5
вместе с VPS и пин-кодом. Довод — в смене модели угроз, а не в осторожности вообще: фаза 1
была только на чтение, и проверки заголовка `Host` хватало, потому что худшим исходом
подмены DNS была утечка данных. С терминалом за тем же адресом тот же вектор означает
**выполнение произвольных команд**, и «сеть только домашняя» такой ценой не окупается.
Авторизация проектируется целиком в фазе 5 — до неё в сеть не выходим.

### 2.2. Раскладка: три колонки

```
проекты  │      работа агента       │  файлы проекта
(слева)  │        (центр)           │    (справа)
```

Переключение проекта слева меняет и центр, и дерево справа.

**Центр** — терминал с сессией Claude Code. Правки агента показываются **прямо в потоке**,
файлом с подсветкой изменённых строк: правка и её результат рядом, без перехода
на другую вкладку.

**Справа** — дерево файлов проекта. Изменённые и новые файлы помечены **по `git status`**.
Клик открывает файл в центре.

Пометка «агент правит этот файл **прямо сейчас**» отменена решением от 01.09.2026, и это
не упрощение, а отказ от несуществующего: такого признака в наборе нет. `PostToolUse` наружу
ничего не пишет, понятия «шаг» в машинном виде не существует — `PLAN.md` перечисляет шаги
прозой. И главное: конвейер обязан работать из системной консоли без пульта, а тогда демон
о правках агента не знает вовсе, то есть пометка молчала бы ровно в половине случаев, ничем
не отличая «агент не правит» от «пульт не в курсе». `git status` отвечает на соседний вопрос
(«что в дереве отличается от коммита»), но отвечает **всегда и одинаково**, кем бы правка
ни была сделана.

**Полоса гейта** под терминалом — не лента событий, а три факта, которые не разрастаются:
взведён или нет, приёмка зелёная или нет, сколько попыток. История событий живёт
на вкладке «Задачи», в карточке задачи.

**Вкладка «Диффы»** остаётся отдельно: в потоке видна правка по одному файлу, во вкладке —
весь дифф задачи целиком. Разные вопросы, обе нужны.

### 2.3. Редактор, а не просмотрщик

Решение от 30.08.2026, меняет прежнее. Правка файлов руками нужна: поправить строку
в конфиге, не поднимая агента.

- редактор: **Monaco** — тот, что в VS Code, вынутый библиотекой. Даёт правку, подсветку,
  поиск и сравнение файлов. Тяжелее Shiki и тянет сборку — это принятая цена;
- диффы: `diff2html` поверх вывода `git diff`;
- файловые операции в дереве: создать, переименовать, скопировать, перенести,
  перетащить извне.

**Сверка при сохранении вместо блокировки.** Решение от 01.09.2026, меняет прежнее.
Пишущих у пульта по-прежнему двое — ты и агент, и VS Code такой задачи не решает, там
пишущий один. Но блокировки файла **не будет**: она опиралась на признак «агент правит
этот файл сейчас», которого в наборе нет (см. §2.2).

Вместо неё — сверка на записи: при открытии файла демон запоминает его состояние, при
сохранении сверяет и, если файл изменился с тех пор, **предупреждает вместо молчаливой
перезаписи**. Правка руками при этом разрешена всегда.

Что это даёт и чего не даёт, надо понимать точно. Это защита **от гонки**, а не от агента:
она ловит момент, когда двое записали одно и то же место, и не даёт потерять чужую правку
незаметно. Помешать агенту писать она не может и не пытается — у него свой процесс и свои
права, пульт ему не начальник.

**Кнопка «Сверить с эталоном»** сравнивает отпечаток набора в проекте с отпечатком
мастер-копии в `~/.claude/agent-kit`. Не номер версии — отпечаток: номер совпадает
при разном составе файлов, и это уже случалось.

### 2.5. Чего нет

Установки набора в проект, профилей, настроек проекта, дашборда сверх пустого состояния,
ответа на `[СТОП]` через API. Ответить на стоп можно — набрав в терминале, как сейчас

**Про гейт:** пульт запускает его команды (`--arm`, `--disarm`, `--status`) как обычные

процесса Claude Code, и красная приёмка не даст завершить ход независимо от пульта.

и ни одно из этого не «забылось». Разделы 2.1–2.7 выше не переписываются: они остаются буквой
фазы, а это — протокол расхождений с ней.

#### Отклонения от буквы контракта

1. **Второго канала нет.** §2.1 называет вторым каналом `claude` в неинтерактивном режиме
   с потоковым JSON и говорит, что «из него живут структурные панели». Решение человека
   от 01.09.2026: **канал один** — псевдотерминал. Структурные панели (полоса гейта, карточка
   задачи, список задач) берутся из журнала событий и состояния задачи, то есть из файлов
   набора, которые демон и так читает. Формулировка §2.1 про второй канал этим решением
   **закрыта**; читать её как невыполненное требование не нужно.

2. **Следствие первого: «правки агента показываются прямо в потоке» (§2.2) реализовано иначе.**
   Правка видна открытием файла из дерева с подсветкой отличий от коммита. Признака «агент
   правит этот файл прямо сейчас» в наборе нет, и это уже записано в самом §2.2; здесь
   называется вторая половина — без второго канала в потоке нечему появляться, потому показ
   и переехал в дерево.

3. **Диаграмма Ганта по агентам из макета не делается.** В `events.jsonl` семь имён событий,
   и «агент начал ход / закончил ход» среди них нет: из `status_changed` восстанавливается
   только грубая привязка, неверная при возвратах. Предусловие — задача набора
   `2026-09-01-sobytiya-zapuska-i-zaversheniya-subagenta-v-zhurnale-imya-mo`. Отложено в фазу 6
   вместе с карточкой задачи (§6.5).

4. **Файловые операции §2.3 сверх создания и сохранения в фазу не вошли** — переименовать,
   скопировать, перенести, перетащить извне. Это **отклонение, а не забывчивость**: каждая
   операция — свой путь записи со своей моделью отказа, а критерий готовности фазы ни одной
   из них не требует. Возврат их в объём — плюс четыре шага записи, и решает это человек.

5. **Показ диффа сделан редактором сравнения из уже привезённой поставки, а не `diff2html`.**
   §2.3 и сводная таблица в конце документа называют `diff2html` (и Shiki, которого в реализации
   нет вовсе — подсветку даёт тот же Monaco). Причина замены: `diff2html` строит **готовую
   разметку** и её надо вставлять в страницу, за которой стоит терминал; редактор сравнения
   получает две стороны текстом, уже проверенные демоном. Меньше зависимостей и ни одного
   присваивания разметки строкой. Сводная таблица намеренно не правилась — она перечисляет
   решения фазы, а расхождение с ними живёт здесь.

#### Отклонения от буквы плана реализации

6. **Регулярного опроса в фазе нет.** План фазы 1 снимал риск «синхронный обход отпечатка
   держит цикл событий» условием «до регулярного опроса фазы 2». Опроса не появилось: список
   проектов обновляется кнопкой, и условие снятия **не наступило**. Отсюда прямое следствие
   для фазы 3: заводить опрос, не перенеся обход в рабочий поток или не разрезав его на порции,
   нельзя — за тем же циклом событий теперь стоит живой терминал.

7. **Запись в файлы под образцами секретов закрыта — это расширение шага плана, а не его
   буква.** План перечислял проверки режима записи поимённо, и секретов среди них не было:
   фильтр был односторонним — закрыт на чтение, полностью открыт на запись. Ревью
   воспроизвело это на стенде (`POST` перезаписывал `.env`, а дерево помечало его доступным
   на запись). Решение человека после ревью: **явный отказ со своей причиной**, симметрично
   уже принятому решению про проект без набора. Выбор между «нельзя никогда» и «можно
   по явному признаку» сделан в пользу первого: чтение обратимо и оставляет след, перезапись
   `.env` не лечится ничем, а признак «можно писать» уезжает в дерево **до** всякого запроса
   и при втором варианте обязан был бы стать истинным — то есть вернуть активную кнопку
   сохранения на файле секретов.

8. **Служебная папка `.git` закрыта в ШЛЮЗЕ, а не только спрятана в дереве.** План требовал
   «папка `.git` не показывается вовсе», но сокрытие имени доступом не управляет: читатель
   зовётся по пути, а в `.git/config` лежат учётные данные (ревью показало чтение строки
   с токеном). Фильтр стоит на обоих режимах и на любом уровне вложенности.

9. **Тело запроса на сохранение считается по потолку, ослабленному вдвое с запасом.** Тело —
   это JSON, где кавычки и не-ASCII раздуваются, и запас в 64 КБ от сырого размера файла
   отбивал бы законные сохранения. Следствие названо честно: код «тело слишком велико» клиенту
   **не доезжает никогда** — по требованию плана соединение рвётся до ответа.

10. **Строки состояния HTTP у отказов подобраны таблицей.** План называет только машинные коды,
    а ответа без числа не бывает; код из закрытого словаря уезжает в теле **как есть**
    и не подменяется. Умолчание таблицы — 403.

#### Что из этого договор с фазой 3, а не просто запись

- **Опроса нет — и заводить его в фазе 3 нельзя без переноса обхода** (пункт 6). Это условие,
  а не пожелание: замер фазы 1 — около 2 с на 7202 файлах, и на эти секунды встаёт терминал.
- **Список изменённого во вкладке диффов считается `git diff HEAD` и неотслеживаемых файлов
  не показывает.** Задача, которая только добавляет файлы, даёт пустую вкладку при непустом
  дереве. Найдено прогоном по критерию готовности. Поддержки неотслеживаемых фаза 2 не даёт
  и в фазе 3 это решение человека; МОЛЧАНИЕ убрано правкой 01.09.2026 — демон отдаёт их число
  полем `untracked`, страница печатает «и ещё N неотслеживаемых» в итоге и под списком.
  Договор с фазой 3 отсюда такой: поле `untracked` в ответе списка диффов — часть формы
  ответа, и полная поддержка обязана его заменить, а не оставить рядом вторым источником.
- **Три отложенных дефекта страницы с названным лечением.** Полотно сравнения молчит, если
  загрузчик редактора не поднялся (нужен показ причины в строке итога — так же, как это уже
  сделано у обычного редактора); терминал дёргается спрятанным теми же двумя ручками
  (изменение размера окна и сворачивание правой колонки), что и полотно диффа, — не мерено;
  редактор сравнения сам переходит на «ленту» при ширине полотна меньше ~900 px, а переключатель
  режима об этом молчит (лечится явным порогом или подписью у кнопки). Все три — кандидаты
  фазы 3.
- **Клиентского действия «закрыть сессию» нет** (решение человека): сессию завершает таймер
  пяти минут. Оболочка фазы 3 при закрытии окна обязана это учитывать — процесс переживёт
  закрытие ещё на пять минут.
- **Linux не поддерживается**: готовых сборок псевдотерминала под него у апстрима нет,
  а сборка на месте потребовала бы компилятора у пользователя. Решение человека от 01.09.2026;
  альтернатива на случай пересмотра названа в плане фазы 2.
- **Машинная приёмка набора (`CCKIT:VERIFY`) не покрывает `pult/**` ни строкой**, и зелёный
  результат приёмки о работоспособности пульта не говорит ничего: в ходе фазы 2 страница была
  нерабочей при зелёной приёмке. Заводить проверки пульта в этот блок — отдельное решение
  человека; фаза 3 не имеет права считать, что это уже сделано.

## PHASE_03_SHELL — оболочка

> **Зачем.** Три вещи, которых страница не умеет: системный диалог выбора папки,
> уведомления и иконка в трее, автозапуск демона.

### 3.1. Что это

Электрон вокруг той же страницы. Оболочка **не содержит логики** — она поднимает демон
и показывает его страницу. Вся работа с файлами и процессами остаётся в демоне, иначе
мобильный доступ отвалится.

### 3.2. Уведомления

Задача ушла в ожидание человека — нативное уведомление с именем проекта, причиной
и возрастом. Клик открывает задачу.

### 3.3. Совместимость

Windows — целевая платформа. Пути с пробелами и кириллицей обязаны работать: у самого
автора проекты лежат в каталогах с пробелами.

### Критерий готовности

- [ ] Пульт открывается и без оболочки, страницей в браузере
- [ ] Диалог выбора папки возвращает путь с пробелами и кириллицей без искажений
- [ ] Уведомление приходит, когда задача перешла в ожидание, и не приходит повторно
- [ ] Закрытие окна не убивает демон, если он был запущен отдельно


### 3.4. Отклонения реализации от буквы фазы

Записаны 02.09.2026 по итогам реализации, по образцу §2.8: **отклонения фиксируются
в контракте, а не остаются в коде молча.** Всё перечисленное — либо решение человека, либо
находка аудита или ревью, и ни одно из этого не «забылось». Разделы 3.1–3.3 выше
не переписываются: они остаются буквой фазы, а это — протокол расхождений с ней.

#### Отклонения от буквы контракта

1. **Упаковки в дистрибутив нет — это НАЗВАННЫЙ НЕЗАКРЫТЫЙ ПУНКТ.** Ни сборщика,
   ни исполняемого файла, ни установщика, ни подписи, ни автообновления: пульт фазы 3
   запускается из исходников. Критерий готовности фазы упаковки не требует, а условие
   «полнота важнее отделки» — про экраны, а не про инсталлятор. **Автозапуска самой оболочки
   при входе в систему тоже нет**; «автозапуск демона», о котором говорит вводка §3, закрыт
   иначе — демон поднимает оболочка.

2. **Оболочка ВСЁ-ТАКИ содержит три вещи, не сводящиеся к «показать страницу».** §3.1 говорит
   «оболочка не содержит логики»; честно назвать, что в ней есть:
   - **поиск системного рантайма** — иначе демон запускался бы под Node с ABI Electron,
     нативный псевдотерминал не грузился бы, и терминал переставал бы подниматься молча;
   - **опрос по расписанию с признаком «уже уведомляли»** — без признака уведомление
     приходило бы каждую минуту, а признак на диске стал бы вторым источником правды
     о состоянии задачи (правило 1 раздела OVERVIEW);
   - **запуск инструмента реестра подпроцессом** — следствие пункта 4 ниже.

   **§3.1 при этом не нарушен:** работа с файлами и процессами проекта осталась в демоне
   и в инструменте кита. Оболочка не читает файлов проекта, не разбирает их и не пишет
   в реестр сама.

3. **Для уведомлений заведён НОВЫЙ лёгкий маршрут на чтение** (`GET /pending`), а существующий
   список проектов для опроса не используется. Это прямое следствие §2.8 пункта 6: `/projects`
   зовёт синхронный обход отпечатка, и опрос по расписанию встал бы на цикле событий, за
   которым стоит живая сессия человека. Замер при живой сессии — 15–18 мс против примерно двух
   секунд у полного обхода.

4. **Маршрута ЗАПИСИ в реестр не заведено, и это решение по итогам аудита фазы.** Первая
   редакция плана предполагала `POST /projects`. Находка: корень из реестра служит границей
   ВСЕМ проверкам пути в демоне — значит клиентский корень снимал бы якорь доверия целиком
   (домашний каталог корнем превращает сохранение файла в запись в автозагрузку, а признак
   `reveal` — в чтение секретов машины). Проект заводит инструмент командной строки
   `pult/tools/registry-add.mjs`, которого оболочка запускает подпроцессом по нажатию человека.
   Правило «любое непустое тело — отказ» **не ослаблено второй раз**: единственный маршрут
   с телом у демона по-прежнему один.

   **Держится это одним свойством, и оно названо: путь рождается в системном диалоге главного
   процесса, а мост страницы не принимает его ни в каком виде** — ни целиком, ни частью,
   ни подсказкой начального каталога. Один необязательный аргумент вернул бы находку целиком,
   и больше её не ловит ничто.

5. **Появилось новое состояние проекта «корень отвергнут» (`root_rejected`)** — это добавление
   к перечню §1.4 и изменение поведения фазы 1. Запрещённый корень **показывается**: запись
   остаётся в реестре и в файле, человек видит причину и что делать, а демон отказывается
   под ней читать и писать (читатель проекта, все маршруты пути, мост сессии, лёгкий маршрут
   ожиданий).

   **Раскладка пометок** (решение человека 02.09.2026, круг 3 аудита): домашний каталог,
   его родитель, каталоги данных приложений и корень диска сверяются **точно** — только сами
   по себе; каталог набора в домашнем, системные каталоги и каталог реестра пульта —
   **вместе с содержимым**. Довод по каталогам данных приложений: запись под такими корнями
   и так требует папки `.claude` в самом корне, а её нет ни у временного каталога,
   ни у папки автозагрузки. Следствие названо вслух: подкаталоги этих каталогов проектом
   быть могут.

   **Две оговорки, которые обязаны ехать вместе с этим состоянием.** Первая: писателей у файла
   реестра **двое** — инструмент и сам демон отметкой просмотра, — и межпроцессной атомарности
   нет; проект, добавленный ровно в окно между чтением и записью, будет затёрт. Вторая:
   сравнение корня строковое и синхронное, поэтому **короткое имя Windows и точка соединения
   тот же каталог под запрет не подводят**; путь, прошедший через инструмент, этим не задет.

6. **Три отложенных дефекта страницы из §2.8 закрыты**, и каждый теперь стережёт постоянная
   машинная проверка со своей отрицательной пробой (`pult/tools/page-check.mjs`, проверки 4–6):
   молчание полотна сравнения при неподнявшемся загрузчике, подгонка терминала в узле без
   места, переключатель режима, обещавший две колонки на ленточном виде. **Поле числа
   неотслеживаемых файлов во вкладке диффов остаётся как было** — полная поддержка
   неотслеживаемых по-прежнему не делается.

7. **Проверки пульта в блок машинной приёмки набора (`CCKIT:VERIFY`) не заводились.** Блок
   правится руками и подтверждается человеком из терминала; фаза 3 его не трогала. Следствие
   надо держать в голове: **зелёная машинная приёмка задачи фазы 3 о работоспособности пульта
   не говорит ничего** — все пять её проверок смотрят на набор.

8. **Платформа проверки — Windows.** Код оболочки кроссплатформенный, целевая платформа
   по §3.3 — Windows, протокол приёмки снят на ней. **macOS не проверялась**, Linux
   не поддерживается решением фазы 2 (готовых сборок псевдотерминала под него у апстрима нет).
   Отсюда же названная граница: оболочка гасит свой демон сама, но оболочка, снятая жёстко,
   до останова не доходит вовсе — **на POSIX брошенный ребёнок переживает родителя**, и это
   не проверялось.

9. **Закрытие окна прячет пульт в значок ТОЛЬКО при годном значке — иначе завершает
   приложение.** Это отклонение от собственного решения фазы («завершение — только явным
   выходом из меню трея»), и появилось оно по находке человека 02.09.2026 в ручном прогоне
   приёмки.

   **Что было:** окно пряталось безусловно, а единственным выходом был пункт меню значка.
   Значка человек не увидел — Windows 11 прячет новые значки в переполнение у часов, — окно
   спряталось, и приложение осталось жить без единого способа его снять, кроме диспетчера

#### Что из этого — договор с фазой 4

Фаза 4 начинает писать, поэтому четыре вещи она обязана **не ослабить**, добавляя свои действия:

1. **Раскладчик кита обязан читать ТОТ ЖЕ белый список состава** (`.claude/ship.list`), что
   и установщики. Разложит другой состав — отпечаток проекта перестанет сходиться с эталоном,
   то есть кнопка «Сверить с эталоном» начнёт врать на каждом проекте.
2. **Запрет записи в папку набора (`write_into_kit` в `resolveTarget()`) и критерий «демон
   не пишет в кит ни байта» ради раскладчика не ослабляются ни на букву.** Раскладка живёт
   отдельным путём со своими правилами и отдельным аудитом, а не расширением шлюза.
3. **Границы корня, окна и моста фаза 4 обязана не ослаблять.** В частности: раскладка
   в новый проект обязана заводить его **тем же инструментом** и **с той же проверкой корня** —
   иначе через новый путь вернётся ровно то, что закрыл пункт 4 выше.
4. **Путь проекта по-прежнему не приходит из запроса и не приходит со страницы.** Появление
   у моста параметра пути — это возврат находки круга 1 аудита фазы 3, и ловить её будет нечем.

5. **Отложенный дефект страницы, найденный фазой 3 и сознательно НЕ вылеченный в ней:
   гонка выбора проекта.** Записан здесь по образцу §2.8 — там фаза 2 записала три своих
   отложенных дефекта, и **именно поэтому** фаза 3 их закрыла.

   **Что воспроизводится:** открыть вкладку диффов, не дождавшись конца выбора проекта.
   `diff.load()` успевает наполнить список файлов, а завершающий `diff.reset()`
   из `selectProject()` (`pult/web/app.mjs`) обнуляет идентификатор проекта уже после этого.
   На экране список есть, а клик по файлу уходит на `/projects//diff` и даёт «отказ демона:
   неизвестно». Воспроизведено при написании проверки 4 инструмента `pult/tools/page-check.mjs`:
   она ловила именно это, пока в неё не добавили ожидание конца выбора (признак — наполненное
   дерево проекта).

   **Чем лечится:** упорядочить выбор проекта так, чтобы сброс вкладки диффов не приходил
   после её загрузки, — либо сбрасывать вкладку в начале `selectProject()`, а не в конце,
   либо считать поколение выбора и отбрасывать устаревший сброс (тем же приёмом, каким
   `open()` в `pult/web/editor.mjs` отбрасывает ответ на устаревший запрос).

   **Почему отложено (решение человека 02.09.2026):** цена дефекта мала — путаное сообщение
   на быстром клике, лечится повторным кликом, ни данных, ни прав не задевает; а правка
   лежала бы в `pult/web/app.mjs`, файле части D, вне шагов части E. Цена **потери записи**
   больше, поэтому запись здесь, а не только в папке задачи.

6. **УРОК ФАЗЫ 3, КОТОРЫЙ ФАЗА 4 ОБЯЗАНА ПРИМЕНИТЬ ДО ПЕРВОЙ СТРОКИ КОДА: проверяется то,
   на что смотрят проверки, а не то, что написано в плане.** Три находки человека прошли мимо
   шести машинных проверок и четырёх кругов ревью не потому, что кто-то схалтурил, а потому,
   что вся аппаратура фазы мерила СТРАНИЦУ в обычном браузере. Оболочки не касалась ни одна
   проверка: её смотрели глазами и по журналу, а журнал на «значка не видно» молчит
   по построению.

   Отсюда правило для фазы 4, где пульт начнёт ПИСАТЬ в чужие проекты: **у каждого нового
   исполняемого куска обязана быть своя аппаратура, а не строчка в протоколе.** Если для куска
   нельзя написать проверку — это первый признак, что и человек его не проверит, и цена
   пропуска в фазе 4 выше на порядок: там ошибка не «окно не закрылось», а «файлы разложены
   не туда».

7. **Уведомление обязано ВЕСТИ, а не просто разворачивать окно.** Найдено человеком
   02.09.2026 на ручной приёмке фазы 3, после того как первые три дефекта были закрыты:
   клик по уведомлению показывает окно — и на этом всё, человек оказывается там же, где был,
   и ищет задачу глазами сам.

   **Почему это дефект, а не украшение.** Смысл уведомления — сократить путь от «меня ждут»
   до «я ответил». Уведомление, которое доводит до окна и бросает, экономит только переключение
   между приложениями, а поиск места решения оставляет человеку — то есть решает меньшую
   половину задачи. Для фазы 5 это ещё дороже: с телефона искать задачу руками неприемлемо.

   **Что уже есть и чего не хватает.** Механизм доставки построен целиком: `notifyOne()`
   в `pult/shell/notify.mjs` знает идентификаторы проекта и задачи и передаёт их мостом,
   `openTaskFromShell()` в `pult/web/app.mjs` переключает проект и раскрывает задачу.
   Не хватает **адреса назначения**: сегодня «то самое место» — карточка задачи, а решение
   человек принимает не в ней. Ответ на `[СТОП]` набирается в терминале, приёмка `DONE.md`
   ждёт вердикта, красная машинная приёмка требует разбора — и это **разные** места.

   **Что обязана сделать фаза 4.** Она заводит ответ на `[СТОП]` через интерфейс (§4.5) —
   то есть именно то место, куда уведомлению следует вести. Требование: **у каждой причины
   ожидания есть свой адрес назначения, и клик ведёт по нему**, а не в общее окно. Причины
   уже перечислены закрытым списком `PENDING_REASONS` в `pult/config.mjs` — семь слов, каждому
   нужен свой адрес. Причина без адреса — это молчание того же класса, что закрывала фаза 3.

### 4.2. Существующий проект: копия, показ, потом раскладка

Три правила, в этом порядке. Нарушение любого делает установку необратимой.

**1. Копия — молча и до первого изменения.** Пульт сам копирует `.claude/`
в `.claude.backup-<дата>` и говорит одной строкой, где она. Не предупреждение
с просьбой сделать бэкап: человек кивнёт и не сделает. Откат должен работать всегда,
а не когда человек оказался предусмотрительным.

**2. Показать, что нашлось, до раскладки.** Чужие агенты в `agents/`, свои команды,
правила в `settings.json`, пользовательский `CLAUDE.md`. Экран «в проекте уже есть вот
это, будет добавлено вот это, ничего из вашего не пропадёт». Не молча.

**3. Аддитивно.** Чужие агенты и команды остаются. Правила в `settings.json`
дополняются — они складываются между уровнями, а не затирают друг друга.

**Чего установка не трогает вовсе:**

- пользовательский `CLAUDE.md` — `CLAUDE.md` набора в чужой проект не едет,
  он исключён из `ship.list` намеренно;
- истории переписки — они живут в `~/.claude/projects/`, а не в проекте. Ни установка,
  ни снос набора их не касаются.

**Единственное настоящее столкновение — содержание чужого `CLAUDE.md`.** Он подгружается
автоматически каждую сессию и может нести инструкции, спорящие с конвейером
(«коммить сразу», «не задавай вопросов»). Пульт это не чинит, но показывает: «в вашем

Файл общий с проектом; вынести его нельзя, это проверено. Поэтому:

- при сносе вычищаются **ровно** перечисленные строки; файл удаляется целиком только

### 4.7. Отклонения реализации от буквы фазы

> Раздел заводится по образцу §2.8 и §3.4 и **наполняется по ходу фазы**. Две записи ниже
> сделаны **до реализации**, решением человека 03.09.2026: они найдены при планировании, а
> папка задачи выведена из-под git и не переживёт её. Реализация этот раздел **дополняет,
> а не заменяет.**

1. **Повторная раскладка возвращает строку игнорирования, которую человек убрал осознанно.**
   Раскладчик дописывает в `.gitignore` проекта строку про папку набора и строку про
   резервную копию по правилу «нет точного вхождения — добавляем». Это правило **не отличает
   «мы ещё не добавляли» от «человек убрал намеренно»**, а убрать её — законное действие:
   команда `/cckit_push-with-me` существует ровно затем, чтобы включить файлы набора в
   репозиторий проекта, и заканчивается словами «сам не правь».

   **Цена:** молчаливое действие над чужим файлом. Направление безопасное — строка **закрывает**
   файлы, а не открывает, — поэтому дефект не критичен и в фазу 4 не лечится. Но он остаётся
   действием, которого человек не просил и о котором ему не сказали.

   **Чем лечится:** признаком «эту строку уже добавляли и её убрали» — то есть той же записью
   о владении, какая ведётся для файла настроек (см. пункт 2), либо явным вопросом человеку
   при повторной раскладке.

2. **Асимметрия владения: в `settings.json` мы помним, что дописали, в `.gitignore` — нет.**
   §4.4 требует перечислять свои строки файла настроек в служебном ключе и вычищать при сносе
   **ровно** их. К `.gitignore` то же правило не применено: строка добавляется, но во владение
   не записывается, и снос её не трогает вовсе.

   Это **осознанный разный подход к двум чужим файлам**, а не недосмотр, и цена у него
   двусторонняя: в файле настроек мы умеем не удалить чужое, но обязаны вести учёт; в
   `.gitignore` учёта нет, поэтому мы не умеем ни убрать своё при сносе, ни отличить своё
   от чужого при повторной раскладке (пункт 1 — прямое следствие).

   **Решать это в фазе 4 не требуется**, но следующая фаза, которая тронет любой из двух
   файлов, обязана выбрать одно из двух: распространить учёт владения на `.gitignore` либо
   записать здесь, почему для него учёт не нужен, — и назвать, что тогда делает снос.

   в наборе нет вовсе**. `cmdStop()` в `.claude/hooks/task.mjs` пишет только ВИД стопа, поля
   или файла под ответ у задачи нет, а имени события «человек ответил» нет в белом списке
   `.claude/hooks/events.mjs`. Пункт критерия «Ответ на `[СТОП]` виден конвейеру и отражён
   в `events.jsonl`» **не закрашен** в протоколе приёмки и записан словами. Это задача НАБОРА.

4. **У раскладчика СВОЙ шлюз и свой каталог.** Запрет `write_into_kit` в `resolveTarget()`
   не ослаблен ни на букву (договор с фазой 4, пункт 2): пишущая раскладка живёт
   в `pult/deploy/**` со своей дверью `deployTarget()`, у которой три места на запись и одно
   на удаление. Чистое — профили, правило ядра, формула отпечатка по составу — лежит
   в `pult/lib/profiles.mjs`, потому что эти функции зовут читатели демона; положи их
   в каталог раскладки, и он вошёл бы в граф импортов демона, покрасив собственную проверку
   каталожного правила.

5. **Раскладка только в СУЩЕСТВУЮЩИЙ проект.** Создание нового проекта с нуля и файл идеи
   в фазу не вошли.

6. **§4.1 в части «контроллер несёт набор внутри себя» НЕ ВЫПОЛНЕН.** Источник раскладки —

   (находка круга 3 аудита). Условие «путь ядра обязан быть в положенном» давало бы

   перечень ядра приходит снаружи, из эталона, и подделать его записью проекта нельзя.

   названа поведением: `owned()` в `.claude/hooks/write-manifest.mjs` считает нашим всё, чьё
   ИМЯ есть в мастер-копии, а при недоступной мастер-копии — весь каталог набора; снос по нему
   унёс бы чужой хук, который additive-копия намеренно не тронула.

## PHASE_05_REMOTE — удалённый доступ, PWA и уведомления

> **Зачем.** Ответить на `[СТОП]` из дома в выходной, не подходя к рабочему компьютеру.
> Без этого асинхронная приёмка из фазы 5 набора остаётся половиной решения: задача
> паркуется, но узнать об этом можно только сев за стол.

### 5.1. Схема без VPN

```
рабочий компьютер          VPS (1 CPU / 2 ГБ)         телефон
   демон + набор    ──────►  посредник       ◄──────  браузер
   исходящее соединение      HTTPS + домен            обычный веб
```

Рабочий компьютер **сам подключается наружу** к VPS. Соединение исходящее: ни проброса
портов, ни разрешений сетевого администратора, работает с любого рабочего интернета.

VPS держит канал и отдаёт наружу обычный адрес по HTTPS. Телефон открывает его
в браузере — обычный веб-трафик, VPN не нужен ни на одной стороне.

**VPS ничего не считает и не хранит.** Он пересылает.

**Предпосылка:** рабочий компьютер должен быть включён и не уходить в сон. Проверяется
до всего остального — пульт может показать настройки питания и сказать прямо, что
машина уснёт через N минут.

### 5.2. PWA вместо приложения

Мобильная версия — **та же самая страница**, установленная на домашний экран. Ни App
Store, ни Google Play, ни аккаунта разработчика. Двух реализаций интерфейса нет и здесь.

Целевая платформа — Android; на iOS работает, проверяется по остаточному принципу.

Что нужно сверх обычной страницы: манифест, сервис-воркер, экран первого захода (адрес,
пин-код, подсказка про домашний экран), состояние «нет связи с рабочим компьютером».

### 5.3. Уведомления

Веб-уведомления через сервис-воркер. На Android штатно; на iOS — только при установке
на домашний экран.

**Слой заменяемый.** Пульт умеет «сообщить человеку», а чем именно — веб-уведомление,
Telegram-бот, письмо — настройка. Архитектуру к одному каналу не привязывать.

### 5.4. Авторизация — не откладывается

За адресом стоит терминал с доступом к оболочке рабочего компьютера. Поэтому:

- пин-код обязателен, а не тумблер, и действует с первого дня — даже когда демон
  слушает только локальную сеть;
- ключи для канала генерирует пульт локально и показывает **одну строку** для вставки
  на сервер. Root-пароль от VPS у человека не запрашивается никогда;
- HTTPS обязателен: без него веб-уведомления не работают вовсе.

### Критерий готовности фазы 5

- [ ] Телефон в мобильной сети открывает пульт без VPN
- [ ] Телефон в **локальной** сети открывает пульт — перенесено из фазы 2 решением
      от 01.09.2026 вместе с пин-кодом: до авторизации демон из петли не выходит (§2.1)
- [ ] Страница ставится на домашний экран и открывается иконкой
- [ ] Уведомление о задаче в ожидании приходит на телефон
- [ ] Без пин-кода не открывается ничего, включая из локальной сети
- [ ] Рабочий компьютер перезагрузился — канал поднялся сам
- [ ] VPS перезагрузился — канал поднялся сам
- [ ] Страница при пропавшей связи показывает это явно

## PHASE_06_MEMORY_DASHBOARD — память, карта и дашборд

### 6.2. Источник дашборда

Только `events.jsonl`. Ничего не считать по прозе артефактов.

### 6.3. Что показывать

Закрыто задач, медиана длительности, доля приёмок с первой попытки, ушло в `blocked`,

### 6.4. Агрегация поперёк проектов

Здесь и только здесь уместен производный индекс — SQLite рядом с реестром пульта,
перестраиваемый из журналов. **Производный, а не источник правды:** удалил — пересобрался.

### 6.5. Карточка задачи из макета — сюда, а не в фазу 2

Замечено 01.09.2026 при первом живом сравнении фазы 2 с макетом. В макете задачи показаны
заметно богаче, чем вышло у нас: список слева с временем «висит N часов», справа полная
карточка с конвейером задачи — полосой по агентам (`planner`, `implementer`, `tester`,
`reviewer`, `security`, `documenter`, `faq-writer`, `gate`) и длительностью у каждого.

**Почему это не догоняется в фазе 2, а ждёт фазы 6.** Полоса по агентам нерисуема сегодняшним
`events.jsonl`: семь разрешённых имён событий описывают статусы задачи, а не ходы агентов —
«агент начал / закончил» среди них нет. Из `status_changed` восстанавливается только грубая
привязка (`planning` ≈ планировщик, `implementing` ≈ исполнитель), и то неверная при возвратах.
Предусловие — задача набора `2026-09-01-sobytiya-zapuska-i-zaversheniya-subagenta-v-zhurnale-imya-mo`:
события `agent_started` / `agent_finished` с именем, моделью и длительностью. Без них полоса
будет не приблизительной, а выдуманной.

Фаза 2 показывает список задач со статусами и чтение артефактов — это её контракт (§2.4),
и он выполнен. Разница с макетом здесь **записана как отложенное, а не как недоделанное.**

### 6.6. Раздел пользовательских инструкций

Оттуда же и того же числа. Статьи `faq-writer` сегодня не показывает никто: агент пишет их
по эталону `artifacts/FAQ_TEMPLATE.md`, а `artifacts/` выведен из-под git и в интерфейсе
пульта не значится. Отдельный раздел в пульте — естественное место, вопрос открыт по двум
пунктам, и оба решаются до реализации, а не в ней:

- **где живут готовые статьи.** Сейчас у них нет договорённого места: каталог артефактов
  рабочий, из него всё уезжает вместе с задачей. Раздел в пульте требует, чтобы у статей
  появился адрес, переживающий задачу;
- **кто их показывает.** Статья пишется конечному пользователю продукта, а пульт —
  инструмент владельца. Раздел полезен как **проверка глазами перед выдачей**, а не как
  витрина для читателя, и это разные интерфейсы.

### Критерий готовности

- [ ] Проект без журнала показывает пустое состояние с объяснением, а не нули
- [ ] Индекс пересобирается с нуля из журналов за одну команду
- [ ] Цифры сходятся с ручным подсчётом по журналу на десяти задачах
