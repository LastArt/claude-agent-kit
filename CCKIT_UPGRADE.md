**Проект:** claude-agent-kit (github.com/LastArt/claude-agent-kit)
**Базовая версия:** 1.5.0
**Целевая версия:** 2.0.0
**Формат:** обзор + шесть фазовых контрактов, каждый выполняется отдельным прогоном конвейера

## 00. OVERVIEW

### Проблема одной фразой

Набор умеет правильно **раздавать роли**, но не умеет **проверять результат машинно** и не умеет
**делать больше одного дела за раз**. Из-за первого нужен человек на каждом этапе, из-за второго
скорость упирается в длину цепочки.

### Три корневые причины

| # | Причина | Следствие | Закрывается фазой |
|---|---------|-----------|-------------------|
| 1 | «Готово» определяется агентом, а не командой с кодом возврата | нельзя уйти от компьютера | Фаза 1 |
| 2 | Артефакты (`PLAN.md`, `REVIEW.md`, `SECURITY.md`) — синглтоны | в системе не может быть двух задач | Фаза 2 |
| 3 | План — плоский чеклист без зависимостей | нечего параллелить, даже имея изоляцию | Фаза 4 |

### Порядок фаз и что даёт каждая

```
Фаза 1  Машинная приёмка (Stop-хук + verify.mjs)      → автономность
Фаза 2  Задачи с идентификаторами (tasks/<id>/)       → многозадачность
Фаза 3  Петля доработки (reviewer → implementer)      → снятие человека с рутины
Фаза 4  Граф зависимостей + worktree                  → параллелизм
Фаза 5  Аудит на плане + безопасность внутри ревью    → качество проверки кода
Фаза 6  Динамический выбор модели + метрики           → стоимость и обозримость
```

Фазы 1–3 независимы от 4–6 и дают основной выигрыш. Если делать только часть — делай 1, 2, 3.

### 2.0.0 в исходном виде не выпускается — решение от 30.08.2026

Карта писалась под мир без пульта. С появлением `cckit-controller` (см.
`CCKIT_CONTROLLER_CONTRACTS.md`) часть работы стала не нужна, и это надо знать, прежде
чем брать очередную фазу.

**Фаза 5 — последняя обязательная.** Она даёт `DONE.md` и статус `awaiting_acceptance`,
то есть асинхронную приёмку. Без неё пульт получает конвейер, который держит сессию
открытой и ждёт человека, — и главная его ценность (ответить с телефона) исчезает.
После фазы 5 работа переключается на пульт.

**Фаза 4 откладывается, а не отменяется.** Параллельные задачи некуда выводить, пока
нет панели. Делать её вместе с интерфейсом, а не до него.

**Фаза 6 частично отменена:**

| Раздел | Судьба |
|---|---|
| 6.1 динамический выбор модели | вероятно устарел — платформа умеет режим Auto сама |
| 6.2 условные `[СТОП]` | **отменяется**: они экономили внимание человека, потому что дёрнуть его дорого. С уведомлением на телефон это дёшево |
| 6.3 метрики | **переезжает в пульт**, дашборд. Фундамент — `events.jsonl` (1.16.0) |
| 6.4 ротация истории | остаётся, но не в этой карте |

**Что в наборе больше не развивается** (пульт делает то же лучше; существующее работает
и остаётся запасным путём):

- `gate-menu.mjs` — консольное окно приёмки;
- `map.html` — самодостаточная страница; киту нужен только `map.mjs --json`;
- `stats.mjs` — печать статистики в чат.

**А что становится важнее: набор должен отдавать данные машинно.** `STATE.md`
с фронтматтером, `events.jsonl`, `map.mjs --json` — это интерфейс для пульта. Каждое
решение проверяется вопросом: сможет ли пульт прочитать это, не разбирая прозу.

---

Статус в этой таблице поддерживается вручную при закрытии каждой фазы. Отметки `[x]`
в рабочем `PLAN.md` живут вне git и исчезают вместе с задачей — эта таблица единственное
место, где состояние переживает закрытие задачи.

### Что НЕ входит в этот план

- Переписывание существующих агентов «под красоту» — трогаем только то, что перечислено.
- Отказ от контрольных точек. Первый `[СТОП]` — утверждение плана — остаётся при
  классах `standard` и `elevated`: это точка продуктового решения, а не проверки.
  Пропускается только на `cosmetic`, и лишь потому, что класс страхован машинным полом
  (§5.1) — пометить задачу с кодом косметикой планировщик не может. Второй `[СТОП]` —
  приёмка результата — в фазе 5 заменяется асинхронным файлом `DONE.md` с чек-листом:
  человек по-прежнему читает и решает, но конвейер не держит сессию открытой в ожидании.

- Стопы, на которые человек не может ответить лучше агента. Вопросы делятся на
  `product`, `technical` и `security` (§5.5); человека спрашивают только по первым.
- Внешние зависимости. Правило «работает сразу после распаковки, без `npm install`» сохраняется
  во всех фазах без исключений.
- Смена формата хранения на JSON/БД. Markdown остаётся: читается человеком, ищется grep'ом.

### Совместимость

Набор ставится в чужие проекты, у пользователей уже есть развёрнутые копии 1.5.0. Поэтому:

- новые файлы добавляются, старые не удаляются до фазы 2 включительно;
- `update.sh` / `update.ps1` должны переносить существующие `artifacts/` в новую структуру
  (миграция описана в контракте фазы 2);
- если новый файл не найден — набор работает по-старому и печатает одну строку-предупреждение,
  а не падает.

## PHASE_01_MACHINE_ACCEPTANCE — машинная приёмка

> **Зачем.** Сейчас `implementer` сам ставит `[x]`, и `reviewer` вынужден проверять, «все ли шаги
> реально сделаны, а не только отмечены». Пока критерий готовности — текст в отчёте, человек
> обязан присутствовать. Эта фаза делает «готово» состоянием, которое проверяется командой.

### 1.1 Новый файл `.claude/hooks/verify.mjs`

Единая точка запуска проверок проекта. Без внешних зависимостей, только `node:child_process`.

**Источник команд** — новый раздел в `PROJECT_PROFILE.md`, машиночитаемый (см. 1.3).

**Логика:**

1. Прочитать блок команд из `PROJECT_PROFILE.md`.
2. Выполнить по порядку, остановиться на первой упавшей.
3. Сформировать `.claude/artifacts/VERIFY.json`:

```json
{
  "ts": "2026-08-20T14:03:11Z",
  "status": "pass",
  "checks": [
    { "name": "lint",  "cmd": "npm run lint",  "code": 0, "ms": 2140 },
    { "name": "test",  "cmd": "npm test",      "code": 0, "ms": 18320 },
    { "name": "build", "cmd": "npm run build", "code": 0, "ms": 9110 }
  ],
  "failed": null
}
```

4. Код возврата: `0` — всё прошло; `1` — упала проверка; `3` — проверок не настроено.

**Режимы запуска:**

```bash
node .claude/hooks/verify.mjs              # прогнать всё, записать VERIFY.json
node .claude/hooks/verify.mjs --only test  # одна проверка
node .claude/hooks/verify.mjs --dry        # показать, что будет запущено
node .claude/hooks/verify.mjs --selftest   # какие проверки настроены и доступны ли бинарники
```

**Важно про таймауты.** Каждая команда запускается с таймаутом (по умолчанию 300 с, переопределяется
в профиле). Зависший тест не должен вешать сессию — это верный способ, чтобы фичу отключили.

### 1.2 Новый файл `.claude/hooks/gate.mjs` — Stop-хук

Заменяет `git-status.mjs` в позиции `Stop` (сам `git-status.mjs` остаётся и вызывается из `gate.mjs`
для печати сводки — не выбрасывай его, он полезен).

**Логика гейта:**

```
Есть активная задача (tasks/<id>/STATE.md со статусом implementing)?
  нет  → напечатать сводку git-status, выход 0        (обычная сессия, не мешаем)
  да   → запустить verify.mjs
           упало  → exit 2 + текст: какая проверка, последние 40 строк вывода
           прошло → отметить в STATE.md verify: pass, exit 0
```

`exit 2` в Stop-хуке возвращает текст агенту и **не даёт ему завершиться**. Это и есть замена
человеческого контроля: агент физически не может закончить с красными тестами.

**Обязательные предохранители** (без них хук превратится в бесконечный цикл):

- счётчик попыток в `STATE.md`; после 3 неудачных подряд — `exit 0` с текстом
  «три попытки не помогли, нужен человек», статус задачи `blocked`;
- если `verify.mjs` вернул `3` (проверок нет) — `exit 0` с одной строкой-предупреждением,
  а не блокировка. Проекты без тестов должны продолжать работать.

### 1.3 Машиночитаемый блок в `PROJECT_PROFILE.md` и `.template.md`

Раздел §2 сейчас — проза. Добавить в него фиксированный блок, который парсит `verify.mjs`:

````markdown
## 2. Команды проекта

<!-- CCKIT:VERIFY -->
```yaml
timeout: 300
checks:
  - name: lint
    cmd: npm run lint
  - name: test
    cmd: npm test
    timeout: 600
  - name: build
    cmd: npm run build
```
<!-- /CCKIT:VERIFY -->

Далее — обычное человеческое описание команд, как сейчас.
````

Парсить встроенным разбором (это плоский YAML на два уровня — регуляркой построчно, без библиотеки).
Блока нет → `verify.mjs` возвращает `3`.

### 1.4 Правки в `settings.json`

```json
"Stop": [{ "matcher": "", "hooks": [
  { "type": "command", "command": "node .claude/hooks/gate.mjs", "timeout": 900 }
]}]
```

Таймаут хука должен быть больше суммы таймаутов проверок, иначе гейт будет обрываться на середине
прогона тестов.

В `permissions.allow` добавить:

```
"Bash(node .claude/hooks/verify.mjs)",
"Bash(node .claude/hooks/verify.mjs --dry)",
"Bash(node .claude/hooks/verify.mjs --selftest)",
"Bash(node .claude/hooks/gate.mjs)"
```

В `permissions.deny` добавить то, что сейчас держится только на честном слове агента:

```
"Bash(git push:*)",
"Bash(git reset --hard:*)",
"Bash(git clean:*)"
```

Правило «push и деплой — на человеке» из `ORCHESTRATOR_PROMPT.md` перестаёт быть пожеланием.

### 1.5 Правки в агентах

**`implementer.md`** — раздел «Проверка синтаксиса» переименовать в «Проверка» и дописать:

> После завершения всех шагов плана запусти `node .claude/hooks/verify.mjs`. Пока он не вернул
> `pass`, задача не выполнена: читай `VERIFY.json`, чини, запускай снова. Не пиши «готово»
> и не сдавай работу с красным `VERIFY.json`.

**`reviewer.md`** — в начало «Как работать» добавить шаг 0:

> Прочитай `.claude/artifacts/VERIFY.json`. Статус `fail` → ревью не начинается, пиши в `REVIEW.md`
> одну строку «🔴 проверки не проходят: `<имя>`» и возвращай задачу. Не ревьюй неработающий код.

### Критерий готовности фазы 1

- [ ] `node .claude/hooks/verify.mjs --selftest` перечисляет настроенные проверки
- [ ] В проекте с заведомо красным тестом агент **не может** завершить ход: хук возвращает exit 2
- [ ] После трёх неудачных попыток хук пропускает и помечает задачу `blocked`
- [ ] В проекте без блока `CCKIT:VERIFY` набор работает как раньше, печатая одну строку-предупреждение
- [ ] `Bash(git push origin main)` отклоняется правами, а не послушностью агента

### Риски

| Риск | Митигация |
|------|-----------|
| Долгие тесты растягивают каждый ход | гейт срабатывает только при статусе `implementing`, не на каждой сессии |
| Бесконечная петля «упало → чини → упало» | счётчик попыток = 3, потом `blocked` |
| Хук ломает работу в проектах без тестов | код возврата 3 → предупреждение, не блокировка |

## PHASE_02_TASK_IDENTITY — задачи с идентификаторами

> **Зачем.** `PLAN.md`, `SECURITY.md`, `REVIEW.md` перезаписываются каждой новой задачей. Это не
> «неудобно» — это архитектурный запрет на две задачи одновременно. Пока он есть, фазы 3 и 4
> невозможны.

### 2.1 Новая структура

```
.claude/
  tasks/
    ACTIVE                        # одна строка: id текущей задачи (или пусто)
    2026-08-20-nesting-import/
      STATE.md                    # статус, попытки, метки времени
      PLAN.md
      SECURITY.md
      REVIEW.md
      VERIFY.json
    2026-08-19-price-markup/
      ...
  explores/                       # стоячий кэш, как сейчас
  artifacts/                      # остаётся ТОЛЬКО как шаблоны (PLAN, REVIEW, FAQ_TEMPLATE)
```

**Идентификатор задачи:** `ГГГГ-ММ-ДД-<slug>`, slug из формулировки задачи, латиница, до 40 символов.
Читается человеком, сортируется хронологически, уникален без счётчиков.

**`tasks/` живёт ВНЕ git — как `artifacts/` и `explores/` сейчас.** Это не деталь оформления,
а условие, без которого фаза 2 возвращает уже закрытую дыру: в `tasks/<id>/` лежат планы, ревью
и аудиты текущих задач, и через `git add -A` или через установщик они уедут в чужие проекты.
Требования те же, что уже действуют для рабочих файлов:

- `.claude/tasks/` в `.gitignore` (и в `.gitignore` проекта пользователя, отдельной строкой);
- каталог материализуется через `hooks/stubs.mjs`, эталоны — в `assets/stubs/`;
- в мастер-копию едет **только пустой указатель `tasks/ACTIVE`** — его раскладывает
  `stubs.mjs --force`, который запускают оба установщика. Папок задач в мастер-копии
  нет и не будет (решение Р10);
- `write-manifest.mjs` заявляет каталог заранее (как уже сделано для `explores/` и страниц),
  чтобы `/cckit_uninstall` снимал его вместе с набором.

### 2.2 `STATE.md` — единственный файл состояния

```markdown
---
id: 2026-08-20-nesting-import
title: Импорт сортамента из XLSX
status: implementing
mode: A
created: 2026-08-20T11:02:00Z
updated: 2026-08-20T14:03:11Z
verify: pass
review_iterations: 1
attempts: 0
branch: cckit/2026-08-20-nesting-import
---

## Журнал

- 09:15 задача заведена
```

Записи в журнал делают `task.mjs status` (на границах шагов) и `gate.mjs` (решения
приёмки). Строки на каждого агента нет намеренно: ручная запись несёт произвольный
текст, поэтому требует подтверждения человека.

**Статусы:** `exploring` → `planning` → `awaiting_approval` → `implementing` → `reviewing` →
`reworking` → `done` | `blocked`.

Это единственное место, где хранится состояние. Никакого дублирования в другие файлы — иначе
они разойдутся.

### 2.3 Новый хук `.claude/hooks/task.mjs`

```bash
node .claude/hooks/task.mjs new "<название>"     # создать задачу, сделать активной, вернуть id
node .claude/hooks/task.mjs status <статус>      # сменить статус активной задачи
node .claude/hooks/task.mjs log "<строка>"       # дописать в журнал
node .claude/hooks/task.mjs close                # done, очистить ACTIVE
node .claude/hooks/task.mjs list                 # таблица задач и статусов
node .claude/hooks/task.mjs path                 # абсолютный путь к папке активной задачи
```

`task.mjs path` — то, что агенты подставляют вместо захардкоженного `.claude/artifacts/`.

### 2.4 `archive-task.mjs` остаётся заглушкой

Удалить его нельзя, пока в природе есть развёрнутые копии 1.5.0–1.9.x: их цепочки зовут скрипт
первым шагом. Файл печатает две строки и выходит с нулём. Удаление — отдельной задачей, когда
такие копии перестанут встречаться.

### 2.5 Миграция для существующих установок

В `update.sh` / `update.ps1` добавить шаг:

1. Есть `artifacts/PLAN.md` с непустым содержимым → создать `tasks/<дата>-migrated/`, перенести
   туда `PLAN.md`, `SECURITY.md`, `REVIEW.md`, статус `done`.
2. Содержимое `artifacts/history/*` → каждая запись в свою папку `tasks/`, статус `done`.
3. Напечатать, сколько задач перенесено.

Миграция идемпотентна: повторный запуск ничего не делает.

### 2.6 Правки в агентах и командах

Везде, где сейчас `.claude/artifacts/PLAN.md`, становится `<папка активной задачи>/PLAN.md`.
Затрагивает: `planner.md`, `implementer.md`, `reviewer.md`, `security-auditor.md`, `explorer.md`
(чтение истории), `ORCHESTRATOR_PROMPT.md`, все команды `cckit_*`.

`explorer` в пункте 0 теперь читает не `artifacts/history/INDEX.md`, а результат `task.mjs list`
плюс grep по `tasks/*/PLAN.md` и `tasks/*/REVIEW.md`.

### Критерий готовности фазы 2

- [ ] `task.mjs new` создаёт папку и делает задачу активной
- [ ] Две задачи существуют одновременно, их артефакты не пересекаются
- [ ] `task.mjs list` печатает таблицу с датами и статусами
- [ ] `update.sh` на копии 1.5.0 переносит историю без потерь и повторный запуск ничего не портит
- [ ] Ни один агент не содержит строки `artifacts/PLAN.md`

## PHASE_03_REWORK_LOOP — петля доработки

> **Зачем.** Сейчас `reviewer` нашёл 🔴 — и дальше ничего не происходит автоматически: человек
> читает выжимку и вручную гоняет задачу обратно. Это самый частый сценарий в реальной работе,
> и он единственный не описан в конвейере.

### 3.1 Формат `REVIEW.md` становится разбираемым

Сохраняем человекочитаемость, добавляем frontmatter:

```markdown
---
verdict: changes_requested   # approved | changes_requested | blocked
critical: 2
important: 1
minor: 4
---

## 🔴 Критично

### 1. `services/nesting.py:142` — нет фильтра по владельцу
...
```

Правило «нет замечаний → файл содержит единственное слово APPROVED» заменяется на
`verdict: approved`. Одно слово было красивым решением, но нерасширяемым: по нему нельзя отличить
«одобрено» от «заблокировано, ревью невозможно».

> **Сноска (1.15.0).** Контракт писан под 1.5.0, когда `map.mjs` ещё не было. Он появился
> позже и разбирает `REVIEW.md` машинно: теперь читает вердикт из шапки и **сохраняет** разбор
> старого формата — задачи из `migrate-tasks.mjs` и копии набора до 1.15 читаются как прежде.
> Ветку `APPROVED` удалять нельзя, пока такие задачи встречаются.

### 3.2 Цикл в оркестраторе

```
implementer → verify (гейт фазы 1) → reviewer
    verdict: approved            → [СТОП: результат человеку] *
    verdict: changes_requested   → review_iterations < 3 ?
                                       да  → implementer (вход: REVIEW.md + PLAN.md)
                                       нет → status: blocked, [СТОП: человеку]
    verdict: blocked             → [СТОП: человеку сразу]
```

\* Фаза 5 заменяет эту остановку файлом `DONE.md` с чек-листом (§5.5). Если фаза 3
делается раньше фазы 5 — оставить `[СТОП]` как есть, менять при переходе к фазе 5.

> **Сноска (1.15.0).** Шага `verify` в цепочке нет и не появилось: приёмку гоняет исполнитель
> после своих шагов и ревьюер нулевым шагом, а гейт стоит Stop-хуком **вне** цепочки. Переходы
> петли завязаны на `GATE_STATE.json`, а не на несуществующий шаг. Второе уточнение: проверку
> «`review_iterations < 3`?» делает не оркестратор, а сам `task.mjs status reworking` —
> он отказывает с кодом 3, и оркестратор в этой ветке ставит `blocked` и зовёт человека.

**Лимит 3 итерации** — не украшение. Без него связка «ревьюер придирается — исполнитель правит»
крутится, пока не кончится контекст.

### 3.3 Режим доработки у `implementer`

Дописать в `implementer.md` раздел:

> **Режим доработки.** Тебе передали `REVIEW.md` с `verdict: changes_requested`. Правь **только
> то, что указано в замечаниях 🔴 и 🟡**. Замечания ⚪ игнорируй, если человек не сказал иначе.
> Не переделывай ничего сверх этого — новые изменения породят новые замечания, и цикл не сойдётся.
> После правок отметь в `REVIEW.md` каждое замечание: `исправлено` / `не согласен: <довод>`.
> Не согласен — это нормально и это не блокирует; решает человек на стопе.

Последний пункт важен: исполнитель, обязанный соглашаться со всеми замечаниями, начнёт ломать
рабочий код ради вкусовщины ревьюера.

### 3.4 Ревьюер видит историю итераций

В `reviewer.md`:

> Это не первая итерация (`review_iterations > 0`)? Прочитай предыдущий `REVIEW.md`. Проверь
> ровно две вещи: устранены ли твои прошлые замечания и не сломало ли исправление что-то ещё.
> **Не поднимай новых тем, которых не было в первой итерации** — если бы они были важны,
> ты бы их увидел сразу. Исключение: 🔴, внесённое самой доработкой.

Без этого правила ревьюер каждый раз находит новое, и три итерации не сходятся никогда.

### Критерий готовности фазы 3

- [ ] `changes_requested` автоматически возвращает задачу исполнителю без участия человека
- [ ] Три неудачные итерации → статус `blocked` и остановка
- [ ] Во второй итерации ревьюер не поднимает новых тем (проверить на живой задаче)
- [ ] Разногласие исполнителя с замечанием не блокирует цикл, а выносится человеку

## PHASE_04_PARALLEL — граф зависимостей и worktree

> **Зачем.** Запрет на параллельного исполнителя обоснован конфликтами записи в одном дереве.
> Изоляция снимает причину, граф зависимостей даёт понимание, что вообще можно разделить.

> **Предусловие — отдельная задача `2026-08-28-yavnyy-identifikator-zadachi-vmesto-active`.**
> Указатель `tasks/ACTIVE` один на проект, и адресация задачи идёт только через него: команда
> из одной сессии переключает статус задачи, заведённой в другой. Это не дефект параллелизма —
> сценарий срабатывает уже сейчас, на двух одновременных сессиях в одном проекте, поэтому
> задача самостоятельная и делается независимо от фазы 4. Суть: `task.mjs` принимает
> идентификатор задачи явным аргументом, `ACTIVE` остаётся значением по умолчанию для
> одиночной сессии, а не единственным способом адресации.
>
> Фазе 4 она нужна закрытой до старта: worktree изолируют файлы, но не состояние — три
> исполнителя при одном глобальном указателе разведут статусы молча, без ошибки.

### 4.1 Группы в `PLAN.md`

Плоский чеклист становится сгруппированным:

```markdown
## Шаги

### Группа A — модель и миграция  `зависит от: —`
- [ ] 1. `models/profile.py` — добавить поле `weight_per_meter`
  - _Проверка:_ `alembic upgrade head` проходит

### Группа B — API  `зависит от: A`
- [ ] 3. `api/profiles.py` — вернуть новое поле в схеме
  - _Проверка:_ `GET /api/profiles` содержит поле

### Группа C — импорт XLSX  `зависит от: A`
- [ ] 5. `services/import.py` — читать колонку веса
  - _Проверка:_ `npm test -- import` зелёный
```

Правило для `planner.md`:

> Группируй шаги по зависимостям, а не по слоям. Две группы независимы, только если **не трогают
> общих файлов** — проверь это буквально, сверив пути. Сомневаешься — объединяй в одну группу:
> ложная независимость дороже потерянного параллелизма. У каждой группы укажи `зависит от:`
> со списком групп или прочерком.

Ключевой критерий — «не трогают общих файлов». Логическая независимость не спасает от конфликта
слияния, а совпадение путей — надёжный машинный признак.

### 4.2 Новый хук `.claude/hooks/worktree.mjs`

```bash
node .claude/hooks/worktree.mjs create <task-id> <группа>   # git worktree add
node .claude/hooks/worktree.mjs merge  <task-id> <группа>   # слить в ветку задачи
node .claude/hooks/worktree.mjs clean  <task-id>            # снять все деревья задачи
```

Деревья создаются вне репозитория проекта: `../.cckit-worktrees/<task-id>/<группа>/`. Внутри
репозитория их держать нельзя — попадут в собственные же обходы файлов и в `git status`.

**Обязательная проверка перед `create`:** проект под git и рабочее дерево чистое. Нет git —
параллельный режим недоступен, оркестратор молча идёт последовательно.

### 4.3 Веерный запуск в оркестраторе

```
Группы без зависимостей, их ≥ 2, проект под git?
  → worktree на группу
  → implementer на группу, ВСЕ ВЫЗОВЫ В ОДНОМ ХОДЕ (это и есть параллельность)
  → дождаться всех
  → merge по очереди; конфликт → стоп, человеку
  → verify один раз на слитом результате
  → следующий ярус графа
```

Потолок — **3 параллельных исполнителя**. Дальше растёт не скорость, а вероятность, что
планировщик ошибся в независимости групп.

### 4.4 Чего делать нельзя

Прямо записать в `ORCHESTRATOR_PROMPT.md`, иначе кто-нибудь (включая тебя через полгода) попробует:

- параллелить группы с зависимостью — даже «они же почти независимы»;
- параллелить исполнителей без worktree, «просто аккуратно»;
- параллелить `reviewer` по частям дифа — ревью целостно по смыслу, разрезанное ревью пропускает
  ровно то, ради чего затевалось;
- запускать `verify` в каждом дереве отдельно — проверяется слитый результат, а не куски.

### Критерий готовности фазы 4

- [ ] План с тремя независимыми группами исполняется тремя агентами одновременно
- [ ] Слияние без конфликтов; конфликт останавливает конвейер, а не «решается» агентом
- [ ] Проект не под git → тихий откат к последовательному режиму
- [ ] `worktree.mjs clean` не оставляет мусора после сбоя на середине

## PHASE_05_SECURITY_PLACEMENT — аудит на плане, безопасность внутри ревью

> **Зачем.** Уязвимости живут в коде: забытый фильтр по владельцу, конкатенация в SQL,
> незакрытый эндпоинт, значение, ломающее границу процессов. Аудитор, читающий только
> `PLAN.md`, их не видит — план может быть безупречен при дырявой реализации. Но и убирать
> проверку замысла нельзя: просчёт архитектуры, найденный после написания кода, стоит
> переписывания, а найденный по плану — одной правки текста.
>
> Поэтому проверок остаётся две, но они разнесены по стадиям и по агентам:
> **замысел проверяет `security-auditor` по плану, реализацию — `reviewer` по коду.**

### 5.1 Класс риска: самооценка плюс машинный пол

`planner` в конце своей работы дописывает в `PLAN.md`:

```markdown
## Класс риска

`elevated` — задача трогает: права доступа, пользовательский ввод, БД
```

Классы: `cosmetic` (текст, стиль, разметка — без нового ввода, прав и данных),
`standard` (логика без прав и внешнего ввода), `elevated` (права, ввод, БД, файлы,
платежи, секреты).

**Класс, объявленный планировщиком, — самооценка, и одной её мало.** Тот же агент, который
писал план, решал бы, проверять ли его: пометив задачу `cosmetic`, он обошёл бы и аудит,
и стоп. Поэтому объявленный класс страхуется машинным полом.

Новая подкоманда:

```
node .claude/hooks/task.mjs class     # читает PLAN.md, считает пол, пишет класс в STATE.md
```

Пол считается по путям, перечисленным в плане, без участия модели:

| Условие | Класс не ниже |
|---|---|
| в плане есть файлы с расширениями кода (`.py .mjs .js .ts .jsx .tsx .go .rs .java .php .rb .sql`) | `standard` |
| в плане есть файлы без расширения, либо пути, содержащие `config`, `conf`, `settings`, `template`, `schema`, `migrations`, `routes`, `auth`, `secrets` | `standard` |
| расширения `.yml .yaml .json .toml .ini .env .conf .sql` вне каталога тестов | `standard` |
| тронуты пути из раздела «Права доступа» `PROJECT_PROFILE.md` | `elevated` |
| тронуты миграции, `.env`, `settings.json`, файлы с ключами и сертификатами | `elevated` |

> Пол по путям — минимум, а не классификатор. Файл с новым маршрутом или правом доступа
> может не попасть ни под одно правило. Пол страхует от небрежной самооценки, а не
> от изобретательной.

Итоговый класс — **больший из объявленного и вычисленного**. Понизить его планировщик
не может; повысить — может и должен, если видит риск, которого нет в списке путей.
Понижение вручную — только человеком, как и в §6.1.

Класс управляет тремя вещами: запускать ли аудит плана (`cosmetic` — нет, остальные — да),
обязателен ли стенд у ревьюера (§5.3), какая модель у агентов (§6.1).

### 5.2 `security-auditor` остаётся на плане

Вход прежний — `PLAN.md`. Выход прежний — `SECURITY.md` со шкалой 🔴/🟡/⚪. Добавляется
frontmatter с тем же полем `verdict`, что у ревьюера (§3.1), чтобы петля обрабатывала оба
файла одинаково.

**Перевод шкалы в вердикт** (без него правило нереализуемо):

| Находки | `verdict` |
|---|---|
| нет находок, либо только ⚪ | `approved` |
| есть 🟡 или 🔴 | `changes_requested` |
| аудит невозможен: план противоречив, неполон или непонятен | `blocked` |

`blocked` — не про тяжесть находки, а про невозможность работать. Тяжесть выражается
шкалой внутри файла.

Адресат возврата — **планировщик**, не исполнитель: на этой стадии кода ещё нет, править
нечего, меняется замысел.

```
planner → task.mjs class → security-auditor   (пропускается при cosmetic)
    verdict: approved            → [СТОП: утверждение плана человеком]
    verdict: changes_requested   → audit_iterations < 3 ?
                                       да  → planner (вход: SECURITY.md + PLAN.md)
                                       нет → status: blocked, [СТОП: человеку]
    verdict: blocked             → [СТОП: человеку сразу]
```

**`audit_iterations`** — поле в `STATE.md`, зеркальное `review_iterations` из §3.2:
увеличивает `task.mjs` при переводе статуса назад в `planning`, той же функцией, что
считает итерации ревью. Заглушка `STATE.md` получает оба поля.

`security-auditor` работает **только на этой стадии**. Права не меняются: `Read / Grep /
Glob / Write`, без `Bash`. Читать `git diff` ему незачем — кода он не смотрит.

### 5.3 Проверку кода делает `reviewer` — вместе с безопасностью

Второго агента на код не заводим. Причина не в экономии, а в том, что теоретическая
проверка кода бесполезна: уязвимости на границах видны в исполнении, а не в чтении. Агент,
который может собрать стенд и провести атаку, у нас уже есть — это `reviewer` с `Bash`.
Заводить второго исполняющего агента ради этого — размывать монополию на запись прод-кода,
которая держится на том, что исполняющих ровно двое.

**Шаг 0 ревьюера дополняется:** прочитать раздел «Класс риска» из `PLAN.md`. Без этого
правила ниже не срабатывают — инструкция «по классу `elevated` сделай то-то» бесполезна
агенту, который класса не видит.

В `reviewer.md` добавляется раздел:

> **Безопасность.** Ты проверяешь не только правильность, но и уязвимость. Отдельный
> аудитор код не смотрит — по коду ты единственный.
>
> **Класс `elevated`: стенд обязателен.** Собери изолированную песочницу — копии
> затронутых файлов во временном каталоге, подложенные входные данные — и проведи
> враждебное значение через весь путь. Границы процессов, argv, файловые имена, ввод
> из внешнего источника: там, где значение переходит из одного слоя в другой, оно
> и ломается. Не смог собрать стенд — так и напиши, с причиной; это находка 🟡,
> а не повод промолчать.
>
> **Класс `standard`: стенд по возможности**, разбор по коду обязателен.
> **Класс `cosmetic`: раздел заполняется одной строкой** «изменения не затрагивают
> ввод, права и данные».
>
> Обязательный минимум разбора при `elevated`: фильтры по владельцу, потолки на итоговые
> величины (а не на сомножители), порядок операций «проверка до записи», утечки в логи
> и query string, санитария входа до границы процессов.
>
> Находки безопасности выноси **отдельным блоком** в `REVIEW.md`, под заголовком
> `## Безопасность`, с той же шкалой 🔴/🟡/⚪. Блок обязателен всегда, включая пустой:
> тогда одной строкой — что проверял и чем.

Раздел «Права/безопасность» в `reviewer.md` **расширяется, а не сокращается** — это
изменение относительно прежней редакции этого документа.

Заглушка `REVIEW.md` получает обязательный раздел `## Безопасность`.

### 5.4 Петля по коду и её границы

Петля та же, что в §3.2 (`reviewer` → `implementer`, лимит 3 итерации, дальше человек),
и находки безопасности идут по ней наравне с остальными.

Одна граница добавляется: **если исправление требует отойти от `PLAN.md`, задача идёт
не исполнителю, а планировщику.** Исполнитель обязан идти строго по плану; правка,
меняющая замысел, — это новый план, а не доработка. Иначе получится код, разошедшийся
с планом, по которому его же и ревьюят.

В `implementer.md`, в раздел «Режим доработки» (создаётся фазой 3 — порядок обязателен),
дописать:

> Замечание нельзя устранить, не отступив от `PLAN.md`? Остановись и скажи об этом
> прямо. Не импровизируй: задача уйдёт планировщику на редакцию плана, и это нормальный
> ход, а не сбой.

### 5.5 Стопы классифицируются по типу вопроса

Принцип, который до сих пор нигде не был записан:

> **Человека спрашивают только тогда, когда правильный ответ зависит от знания предметной
> области, которого нет ни в коде, ни в плане.** Всё остальное — работа конвейера. Стоп,
> на который человек не может ответить лучше агента, — это дефект конвейера, а не
> контрольная точка.

Три типа вопросов:

| Тип | Пример | Кто решает |
|---|---|---|
| `product` | «имя расчёта в query string или отдельным запросом — цена такая-то» | человек |
| `technical` | «ревьюер требует переписать функцию, исполнитель не согласен» | конвейер: петля, затем `blocked` |
| `security` | «найдена дыра класса `elevated`» | конвейер: петля; после трёх итераций — человек, но с вопросом «продолжаем или бросаем», а не «что делать» |

Тип проставляется явно: поле `stop_kind` в `STATE.md`. Формулировка вопроса человеку
даётся **в терминах последствий, а не кода**: «название заказа окажется в логах, которые
читают администраторы» — это вопрос к человеку; «значение не санитизируется до границы
процессов» — не вопрос, а работа.

Первый `[СТОП]` — продуктовый по определению, поэтому и остаётся (§5.6).

### 5.6 Первый `[СТОП]` остаётся, второй становится асинхронным

**Первый `[СТОП]` — утверждение плана.** Остаётся при `standard` и `elevated`. Аудитор
отвечает, безопасен ли план, но не отвечает, тот ли это план вообще: выбор между двумя
рабочими решениями с разной ценой — не проверка, а продуктовое решение. Пропускается
только при `cosmetic`, и это безопасно ровно потому, что класс страхован машинным полом
(§5.1): пометить задачу с кодом косметикой планировщик не может.

**Второй `[СТОП]` — приёмка результата.** Заменяется файлом в папке задачи:

```
.claude/tasks/<id>/DONE.md
```

Не синглтон: файл принадлежит конкретной задаче, как `PLAN.md` и `REVIEW.md` после фазы 2.

**Пишет его оркестратор** по заглушке из `assets/stubs/`. Не ревьюер — у него нет `Write`.
Не исполнитель — отчёт о собственной работе, написанный тем, кто её делал, теряет смысл.

Содержимое:

- что сделано, одним абзацем;
- перечень затронутых файлов;
- вердикт ревью и блок «Безопасность» из `REVIEW.md` — что нашли и чем закрыли;
- **чек-лист человека**: что проверить руками до слияния, по пунктам, с пустыми
  квадратами;
- что осталось незакрытым и почему.

**Статус задачи** после записи — новый, `awaiting_acceptance`. Ни `done` (человек ещё не
решил), ни `reviewing` (ревью окончено). Добавляется в список `task.mjs`; `task.mjs close`
переводит из него в `done`.

**Взвод гейта снимается при записи `DONE.md`.** Гейт нужен, чтобы агент не завершил ход
с красными проверками; после `DONE.md` работа агента окончена, и держать взвод не за чем.
Без этого TTL шесть часов уронил бы задачу в `blocked`, пока человек читает файл в своём
темпе — то есть асинхронная приёмка не работала бы вовсе. Побочно это закрывает давнее
замечание: гейт, остающийся взведённым на закрытой задаче.

Машинный гейт как механизм никуда не девается — он не человеческая точка и внутри хода
работает как работал.

**`DONE.md` не уезжает наружу.** Он несёт блок безопасности, то есть перечень слабых мест
проекта. В `/cckit_push-with-me` добавляется исключение — по той же причине, по которой
туда уже не пускают `tasks/**`.

**Пятый файл задачи тянет за собой** (иначе формат разъедется по задачам):

- заглушка `assets/stubs/DONE.md` и её раздача в `task.mjs new`;
- `map.mjs` читает четыре известных имени файлов на задачу (решение Р11 фазы 2C) —
  станет пять;
- классификация в `write-manifest.mjs` и подсчёт памяти в `uninstall.mjs`;
- `/cckit_recall` получает новый источник.

### Открытые вопросы фазы 5

**Точка перехвата на границе раунда доработки.** Долг, оставшийся от фазы 3 (1.15.0).
Формулировка ниже записана дословно в `reviewer.md`, `implementer.md` и `CHANGELOG.md` —
не пересказывайте её своими словами, расхождение здесь меняет ответ на вопрос о том,
кто отвечает за то, что красное дерево не уедет дальше.

**Машинная приёмка в раундах доработки.** Stop-гейт срабатывает **не более одного раза
за задачу**: на первом завершении хода после взвода. Зелёный прогон уводит его в
`status: verified`, и дальше он не проверяет ничего: в `decide()` стоит короткое замыкание
на `status: verified` (`gate.mjs`). Границы раунда
для приёмки не существует: `SubagentStop` в наборе не используется, а петля доработки
укладывается в один ход оркестратора. Поэтому машинную проверку круга дают **два
независимых полных прогона** блока `CCKIT:VERIFY`: прогон исполнителя после его правок
и прогон ревьюера нулевым шагом. `--fresh` прогоном **не является** — он сверяет свежесть
чужого результата и без git не работает вовсе, поэтому в раундах доработки нулевой шаг
ревьюера делает полный `verify.mjs`. За красное дерево отвечает **исполнитель**; ревьюер
ловит пропуск. Закрыть это по-настоящему может только точка перехвата на границе раунда
(`SubagentStop` либо снятие короткого замыкания на `status: verified`) — открытый вопрос
фазы 5.

Перевзвод гейта как решение рассмотрен и **отклонён**: `--arm` пишет состояние заново,
обнуляя `attempts` и стирая `status: blocked`, то есть лечит одну дыру, открывая другую.
**`--disarm` и перевзвод — разные механизмы, и путать их нельзя:** `--disarm` снимает взвод
целиком и применяется на **конце** работы (в фазе 5 — при переходе задачи
в `awaiting_acceptance`, с ключом `--if-task` и условиями внутри `modeDisarm`), а `--arm`
пишет состояние заново **в середине**, обнуляя `attempts` и стирая `blocked`. Первое фаза 5
сделала; второе остаётся отклонённым.

**Фаза 5 эту границу не закрыла — и это записано честно.** Граница раунда доработки машинно
**не перехватывается**: `SubagentStop` в наборе не используется, а петля доработки укладывается
в один ход оркестратора. Круг держат два независимых полных прогона блока `CCKIT:VERIFY` —
прогон исполнителя после его правок и прогон ревьюера нулевым шагом. Отдельная задача заведена
2026-08-29: `2026-08-29-tochka-perehvata-na-granice-raunda-subagentstop-i-mashinnyy-`,
статус `exploring`. Решать в ней: `SubagentStop`, снятие короткого замыкания
на `status: verified` или явный прогон приёмки между агентами.

**Остаточный путь фазы 5: перевзвод как способ снять красную приёмку.** Записываем прямо,
потому что фаза 5 его не закрыла. `Bash(node .claude/hooks/gate.mjs --arm)` стоит
в `permissions.allow` и выполняется бесшумно, а `modeArm` перезаписывает состояние целиком:
`status: implementing`, `attempts: 0`, `verify: 'none'`. После него условие `unverified`
из `modeDisarm` законно пропускает снятие, и путь «подделать вердикт → закрыть задачу»
удлиняется с трёх команд до четырёх. Правами это **не закрыто**. Чем смягчено: `modeArm`
пишет событие `gate_armed`, поэтому перевзвод посреди работы виден в `events.jsonl` рядом
с последующим `status_changed`, а обнулённый без единого зелёного прогона `attempts` виден
там же. Варианты закрытия — убрать `--arm` из `allow` (тогда взвод спрашивает человека каждый
раз) либо научить `--arm` помнить прежнее красное состояние; оба меняют рычаг человека
и в фазу 5 не входили.

**Классификация по содержимому плана.** Пол §5.1 считается по путям и потому слеп к тому,
что в этих путях делается: `services/report.py`, собирающий SQL конкатенацией, и он же,
меняющий подпись в шапке отчёта, для пола неразличимы. Развитие — читать текст плана
и поднимать класс по упоминаниям авторизации и прав, SQL, запуска подпроцессов, внешних URL.

В фазу 5 не входит намеренно. Правило по содержимому вырождается в поиск по словам: класс
поднимается на каждом «пароле» в комментарии, пол начинают понижать руками — и он перестаёт
страховать вообще. Возвращаться к этому после того, как накопится журнал: по нему видно,
сколько задач пол поднял зря, а сколько пропустил.

## PHASE_06_ECONOMY — модель по классу риска, условные стопы, метрики

### 6.1 Модель выбирается динамически

Сейчас модель прибита к роли: `planner`, `implementer`, `reviewer`, `security-auditor` — opus.
Четыре тяжёлых прохода на каждую задачу, включая правку опечатки в тексте кнопки.

Front-matter агента поддерживает только одно значение `model`, поэтому выбор делает **оркестратор**,
явно указывая модель при вызове:

| Класс риска | planner | implementer | reviewer | auditor |
|-------------|---------|-------------|----------|---------|
| `cosmetic`  | haiku   | sonnet      | sonnet   | не запускается |
| `standard`  | sonnet  | opus        | sonnet   | sonnet |
| `elevated`  | opus    | opus        | opus     | opus |

Колонка `auditor` относится к аудиту **плана** (§5.2) — единственной стадии, где он
работает. Запускать его или нет, решает §5.1, а не эта таблица.

Эскалация класса вверх разрешена в любой момент (explorer нашёл больше файлов, чем ожидали),
понижение — только человеком.

### 6.2 `[СТОП]` становится условным

Сейчас два обязательных стопа на каждую задачу. Правило:

| Класс | Стоп на план |
|-------|--------------|
| `cosmetic` | нет |
| `standard` | да |
| `elevated` | да, всегда |

Колонки «стоп на результат» здесь больше нет: фаза 5 заменила его файлом `DONE.md`
и статусом `awaiting_acceptance` (§5.6). Стоп на план при `standard` остаётся —
продуктовые решения бывают и там, а прежняя формулировка «нет, если аудит без 🔴/🟡»
путала проверку безопасности с продуктовым выбором.

Плюс глобальный тумблер в профиле:

```yaml
autonomy: guarded   # guarded (как сейчас) | auto (по таблице выше) | manual (стоп везде)
```

По умолчанию `guarded` — незнакомый проект не должен внезапно начать работать сам.

### 6.3 Метрики, которые влияют на решения

`stats.mjs` расширяется и читает `tasks/*/STATE.md`:

```
Задач завершено:            34
С первого ревью:            19  (56%)
Среднее число итераций:     1.7
Заблокировано:               3  (8%)
Средний verify до зелёного: 2.1 прогона
Чаще всего падает:          test (14 раз), lint (5)
Параллельных задач:         сред. 1.3, макс. 3
```

Без этих цифр любое дальнейшее улучшение конвейера — вкусовщина. «С первого ревью» — главная
метрика качества планировщика: падает она, значит, планы стали хуже, а не исполнитель разленился.

### 6.4 Ограничение роста истории

`explorer` грепает по всем задачам. Через сотню задач это медленно и шумно. Правило:

- `task.mjs list` отдаёт только последние 30 задач, остальное по флагу `--all`;
- задачи старше 90 дней сжимаются в `tasks/_archive/ГГГГ-КВ.md` — по абзацу на задачу:
  название, дата, суть решения, чем закончилось;
- `explorer` грепает свежие задачи целиком, архив — только по заголовкам.

## Как это выполнять

Каждая фаза — отдельный прогон твоего же конвейера, в режиме B:

```
/cckit_feature Фаза 1 из CCKIT_UPGRADE.md — машинная приёмка
```

Порядок обязателен для 1 → 2 → 3 (каждая опирается на предыдущую) и для 4 после 2.
Фаза 5 требует фазы 3 (переиспользует `verdict`, `review_iterations` и раздел «Режим
доработки») и фазы 2 (`tasks/<id>/`, `task.mjs`). Фаза 6 — после 5: её таблицы опираются
на класс риска и на `DONE.md`.

**Тестировать на развёрнутой копии**, а не в репозитории набора — правило из твоего `CLAUDE.md`
здесь особенно критично: гейт, который блокирует завершение хода, при ошибке в коде заблокирует
и работу над самим набором.

Заведи для проверки два подопытных проекта: один под git с работающими тестами (проверяет
счастливый путь и параллелизм), второй без git и без тестов (проверяет, что набор не разваливается
там, где проверять нечем). Второй важнее — именно на нём ломаются такие изменения.
