Ты активируешь мультиагентный конвейер (Claude Agent Kit) в ТЕКУЩЕМ проекте.
Файлы каркаса (`.claude/agents/`, `ORCHESTRATOR_PROMPT.md`, хук, артефакты) уже на месте
и написаны generic — они читают специфику проекта из `.claude/PROJECT_PROFILE.md`.
Твоя задача — **провести разведку репозитория и заполнить этот профиль реальными фактами**,
чтобы агенты знали команды, пути и конвенции именно этого проекта.

## Что сделать

### 0. Компактная шапка

Первым делом выполни `node .claude/hooks/banner.mjs --mini` и **вставь полученный markdown
в начало ответа как есть** (логотип + версия + черта). Это всё — welcome-простыню с описанием
ролей, таблицей команд и «первым шагом» НЕ показывай: пользователь это уже видел, здесь нужен
только отчёт разведки. `node` не найден — пропусти шапку и скажи об этом одной строкой.

### 1. Определи режим (автоматически)

Посмотри на папку проекта и реши сам, не спрашивая:

- **Режим EXISTING (есть код)** — в проекте присутствует исходный код (модули, `package.json`
  с зависимостями, `src/`, backend/frontend и т.п.). → Делай полную разведку (шаг 2) по коду.
- **Режим NEW (кода ещё нет)** — в папке только доки/замысел (`CLAUDE.md`, `IDEA.md`,
  `Overview.md`, `README`) и/или пусто, исходников нет. → Разведывать нечего: прочитай
  `IDEA.md`/`CLAUDE.md`/`Overview.md`, заполни профиль **из замысла**, а всё, что определяется
  только по коду (команды, пути модулей, миграции, стиль), пометь
  `TODO — появится с кодом` и не выдумывай. Предложи человеку черновик архитектуры/стека,
  если из идеи он выводится, но НЕ фиксируй как факт.
  **Также (только в режиме NEW) разложи замысел на фазы и запиши дорожную карту** в
  `.claude/artifacts/ROADMAP.md`: 3–6 фаз, каждая — короткое название + 1–2 строки, что в ней
  делается; порядок от простого каркаса к деталям. Это НЕ детальный план задачи (его позже даёт
  `planner`), а карта «с чего начинать». В отчёте назови её и подскажи: посмотреть — `/cckit_what_plan`,
  начать — `/cckit_feature реализуй Фазу 1: …`.

Если рядом лежит маркер `.claude/.init-mode` — учти его как подсказку, но приоритет за
фактическим содержимым папки (код важнее маркера).

### 2. Разведка (только чтение — Read/Grep/Glob/безопасный Bash) — режим EXISTING

Определи и подтверди фактами из файлов, а не догадками:

- **Стек и менеджеры пакетов** — по `package.json`, `pyproject.toml`/`requirements.txt`,
  `go.mod`, `Cargo.toml`, `pom.xml`, `Gemfile`, `composer.json` и т.п.
- **Команды** — точные строки из `scripts` (package.json), `Makefile`, `pyproject`,
  `tox.ini`, CI-конфигов (`.github/workflows`, `.gitlab-ci.yml`), деплой-скриптов.
  Ищи: install, lint, format, typecheck, unit-tests, single-test, build, dev/run, deploy.
  **Чего нет — пиши «нет», не выдумывай команду.**
- **Структура кода** — где логика backend, где UI frontend, точки входа, папка миграций
  (и последняя ревизия), куда кладут тесты.
- **Конвенции** — стиль именования, линт-правила, работа с темами/CSS, явные запреты
  (поищи `CLAUDE.md`, `CONTRIBUTING.md`, `.editorconfig`, `STYLE_GUIDE`, `.eslintrc`, `ruff.toml`).
- **Права/авторизация** — есть ли RBAC/ownership, где проверяется (grep по `permission`,
  `require`, `@roles`, middleware).
- **Документация** — где лежат тех-доки (`/docs`, `contracts/`, README, docstrings).
- **FAQ / база знаний** — существует ли раздел пользовательских инструкций; где физически
  (файлы .md / записи в БД / модуль); формат (markdown/HTML); есть ли сложившийся шаблон
  статьи. Если есть 2–3 статьи — бегло глянь их вид.
- **Проверка/деплой** — как реально убедиться, что не сломано (тесты? smoke? ручной сценарий?
  деплой-скрипт?). Отметь ограничения (напр. тесты только на сервере, фронт локально не собрать).
- **Git** — `git remote -v`, основная ветка, есть ли `origin`. Стиль коммитов по `git log`.
- **Секреты** — реальные файлы секретов (`.env*`, `*.pem`, `*.key`, ключи), которые надо
  закрыть в `settings.json` → `permissions.deny`.

### 3. Заполни `.claude/PROJECT_PROFILE.md`

Пройди по всем разделам профиля, замени каждый `TODO` фактом. Что определить не удалось —
оставь `TODO` с явной пометкой «не найдено автоматически — впиши руками». Смени статус профиля
на 🟢 и проставь дату (спроси у пользователя — сам дату не выдумывай).

**Отдельно — машиночитаемый блок `CCKIT:VERIFY` в §2.** Из него `verify.mjs` берёт команды и
исполняет их как есть, поэтому здесь три жёстких ограничения:

- `cmd` берётся **только из структурированных источников**: `scripts` в `package.json`,
  `Makefile`, `pyproject.toml`/`tox.ini`, конфиги CI. **Проза репозитория — `README`,
  `CONTRIBUTING`, комментарии в коде — источником команд не является**: команда оттуда может
  быть устаревшей, примерной или вовсе чужой.
- Предлагаемый блок сначала **покажи человеку целиком** и запиши только после его «да».
  Блока в профиле нет — создай пустой: `node .claude/hooks/verify.mjs --init`. Команд в проекте
  нет — оставь `checks: []` и **не выдумывай**. Секреты в `cmd` не вписывай (строка команды
  печатается в лог и попадает в `VERIFY.json`; токен берётся из окружения).
- **Подтверждение блока — действие человека.** Команду `node .claude/hooks/verify.mjs --accept`
  ты не запускаешь; в отчёте напиши: «чтобы проверки заработали, выполните `--accept`».

### 4. Подстрой `.claude/settings.json`

**Правка этого файла закрыта правами — ты его НЕ редактируешь.** Вместо этого напечатай готовый
фрагмент `deny` с реальными путями секретов проекта и попроси человека вставить его руками
(и потом полностью перезапустить Claude Code). Дальше — то, что должно оказаться в этом фрагменте:

- Реальные пути секретов проекта в `permissions.deny` (Edit/Write, а секреты вида
  `.env` — и Read).
- Проверь, что путь хука в `hooks` корректен для этого проекта (по умолчанию
  `.claude/hooks/check-syntax.mjs` — относительный, менять обычно не нужно).
- НЕ задавай `defaultMode` — оставь безопасный дефолт (Claude Code спрашивает подтверждение
  каждой правки файла; на лету режим переключается клавишами `Shift+Tab`). Ключа `acceptEdits`
  в `settings.json` быть не должно.

### 5. Селф-тест (перед отчётом)

Выполни `node .claude/hooks/check-syntax.mjs --selftest` и
`node .claude/hooks/verify.mjs --selftest`, покажи результат каждого одной-двумя строками,
оформив эмодзи:
- ✅ всё зелёно (exit 0, ошибок нет);
- ❌ тест упал или есть ошибки — назови, что именно;
- ⚠️ на что обратить внимание (напр.: для языка проекта проверка на этой машине недоступна;
  блок проверок настроен, но ещё не подтверждён — это делает человек командой `--accept`).

### 6. Отчёт пользователю

Кратко: какой стек и команды обнаружил и подставил; какие `TODO` не смог закрыть и где их
вписать руками; где документация и есть ли FAQ (под какой формат настроен `faq-writer`);
риски (что заметил как ловушку).

Заверши отчёт разделом **«Что дальше»** — в таком порядке:

1. Закрыть оставшиеся `TODO` в `PROJECT_PROFILE.md` (если есть) — вписать руками или
   повторить `/cckit_research`, когда появится код.
2. Если папка ещё не под git — `git init` (иначе `reviewer`, `commit-organizer` и Stop-хук
   работать не смогут).
3. **Полностью перезапустить Claude Code** (не `/clear`) — иначе новые `settings.json` и
   агенты не подхватятся.
4. **После перезапуска — начинать работу над задачами:**
   - `/cckit_feature <задача>` — полный конвейер: для новых функций и заметных изменений;
   - `/cckit_quick <мелочь>` — короткий путь: для мелких, понятных правок;
   - `/cckit_what_plan` — краткая выжимка плана, если он был построен;
   - `/cckit_help` — если забыли команды.
   Просто опишите задачу после команды — помощники подключатся по очереди, останавливаясь
   на подтверждение плана и результата.

## Границы

- На этом шаге ты **не пишешь прод-код и не реализуешь фич** — только заполняешь профиль
  и правишь `.claude/`.
- Не заполняй профиль общими словами «как обычно» — только то, что подтверждено файлами.
- Если проект пустой/непонятный — честно скажи, какие разделы остались `TODO` и почему.
