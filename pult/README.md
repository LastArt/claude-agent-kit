# Пульт — демон, рабочее место, оболочка и действия (фазы 1–4)

Локальный сервис на Node, который знает про все проекты сразу, умеет читать их `.claude`,
отдаёт страницу рабочего места в три колонки, держит живую сессию Claude Code
в псевдотерминале и правит файлы проекта со сверкой. Реестр путей к проектам лежит в профиле
пользователя, а кит каждого проекта вычитывается заново на каждый запрос; всё это
на `127.0.0.1:7331`.

С фазы 3 вокруг этой же страницы есть **тонкая оболочка на Electron** (`pult/shell/`): окно,
иконка в трее, системный диалог выбора папки и нативные уведомления «задача ждёт человека».
Логики в ней нет — она поднимает демон ОТДЕЛЬНЫМ процессом системного Node, показывает его
страницу и запускает готовый инструмент кита. Пульт по-прежнему полностью работает и без неё,
страницей в браузере.

С фазы 4 пульт **действует**: раскладывает набор в чужой проект по профилю, ведёт резервную
копию, сливает свои строки с чужим файлом настроек, снимает положенное по собственной записи
и запускает команды набора, показывая их вывод дословно. Раскладку и команды запускает
**оболочка** подпроцессами; у демона от этого не появилось ни одного нового маршрута.

**ФОРМУЛИРОВКА, КОТОРАЯ ИНАЧЕ ПЕРЕЖИВЁТ СВОЮ ПРАВДУ.** «Пульт не пишет в набор» с фазы 4
НЕВЕРНО: раскладчик пишет туда по замыслу, своим шлюзом и со своими проверками. Верно
и охраняется по-прежнему другое — **ДЕМОН не пишет в набор ни байта**; это и меряет
`pult/tools/no-write-check.mjs`. Разница не словесная: у демона и у раскладчика разные двери,
разные правила и разные доказательства.

Фазовые контракты пульта лежат в `CCKIT_CONTROLLER_CONTRACTS.md` в корне репозитория, разделы
`PHASE_01_DAEMON` (демон), `PHASE_02_WORKPLACE` (рабочее место), `PHASE_03_SHELL` (оболочка)
и `PHASE_04_ACTIONS` (действия). Сеть, пин-код и телефон — фаза 5; карта памяти и дашборд —
фаза 6.

## Границы фазы 2: что демон делает и чего не делает

Фаза 1 была **только чтением**, и это было структурной гарантией: методов записи у API
не существовало вовсе. Читать прежние формулировки как описание сегодняшнего дня **нельзя** —
фаза 2 принесла три вещи, каждую со своей моделью отказа: страницу, доступ к оболочке машины
через вебсокет и запись в файлы чужого проекта.

- **Метод записи ровно один:** `POST /projects/:id/file` — сохранение файла проекта со сверкой
  токена. Общая проверка «любое непустое тело — отказ» ослаблена ТОЧЕЧНО: тело читается только
  на этом маршруте и только при типе `application/json`. Все прочие методы, кроме `GET`, — 405.
- **ДЕМОН в `.claude` любого проекта не пишет ни байта**, и держится это не отсутствием
  методов, а проверками шлюза — см. раздел про принятые риски, пункты 6 и 7 (сам шлюз
  и полный список закрытого на запись). С фазы 4 это утверждение читается БУКВАЛЬНО:
  раскладчик пульта в папку набора пишет, но он живёт вне демона, ходит своей дверью
  (`deployTarget()` в `pult/deploy/gate.mjs`) и запускается оболочкой подпроцессом.
- **Вторая запись демона на диск та же, что была:** время последнего просмотра **в своём
  реестре** при запросе одного проекта. Реестр принадлежит пульту и лежит в профиле
  пользователя.
- **Статусы задач демон не меняет, на `[СТОП]` через API не отвечает, файлы кита не правит.**
  Ответить на стоп можно — набрав в терминале пульта, как раньше в VS Code.
- **Сессия псевдотерминала — это доступ к оболочке машины**, и вид сессии приходит от клиента
  только СЛОВОМ из закрытого словаря: команда, аргументы и рабочий каталог вычисляются
  на демоне.

## Запуск

```
node pult/server.mjs                       поднять демон (страница — на http://127.0.0.1:7331/)
node pult/tools/registry-add.mjs <путь>    завести проект в реестре
node pult/tools/fingerprint-parity.mjs     сверить копию алгоритма отпечатка с оригиналом
node pult/tools/no-write-check.mjs [N]     доказать, что ДЕМОН не пишет в кит ни байта
node pult/tools/write-scope-check.mjs      доказать границу записи демона по проекту целиком
node pult/tools/page-check.mjs             проверить страницу в headless-браузере на своём стенде
node pult/tools/shell-check.mjs            проверить оболочку: значок, выход, процессы после выхода

node pult/tools/kit-deploy.mjs --into <путь> --profile <ключ>   разложить набор в проект
node pult/tools/kit-deploy.mjs --report --into <путь>           посмотреть, что в проекте есть
node pult/tools/kit-remove.mjs --from <путь> [--dry]            снять положенное пультом
node pult/tools/deploy-check.mjs           проверить раскладку: семь проверок, 25 проб
node pult/tools/kitrun-check.mjs           проверить запуск команд набора: шесть проверок
node pult/tools/wizard-check.mjs           проверить мастер установки: слот, отказы, путь
node pult/tools/check-all.mjs              ВСЕ ПЯТЬ проверок разом, итог одной строкой
node pult/lib/fs-safe.mjs --selftest       показать отказы безопасных примитивов и шлюза
node pult/lib/origin.mjs --selftest        показать сверку происхождения на выдуманных заголовках
```

У инструментов те же имена в `npm run` (`parity`, `nowrite`, `writescope`, `pagecheck`,
`shellcheck`, `deploycheck`, `kitruncheck`, `wizardcheck`), а `npm --prefix pult run check` зовёт
все пять проверок пульта разом.

**`check-all.mjs` — точка входа ПЕРЕД КОММИТОМ, а не часть машинной приёмки набора.** Инструменты
пульта в блок `CCKIT:VERIFY` не заводятся осознанно (решение человека 03.09.2026): блок гоняется
Stop-гейтом на каждом завершении хода с потолком 120 секунд, а эти проверки идут минутами —
в блоке они выключили бы приёмку целиком. Итог точки входа различает **три** исхода: «зелено»,
«НЕ ДОКАЗАНО ПОЛНОСТЬЮ» (с названием непроведённого словами) и «КРАСНО»; «не доказано»
в «зелено» она не превращает.
Проверка страницы поднимает СВОЙ стенд на свободном порту и в чужой демон не стучится: боевой
демон человека при этом можно не останавливать. Ей нужен установленный Chrome, Edge или
Chromium (путь можно задать переменной `CCKIT_CHROME`); браузера нет — она честно говорит
об этом и выходит кодом 3, ничего не «проверив».

Нужен Node 18 или новее. С фазы 2 у демона **есть** зависимости — псевдотерминал и кадрирование
вебсокета, — поэтому перед первым запуском нужен `npm ci` в каталоге `pult`. Состав, версии,
происхождение и sha256 привезённых сборок страницы описаны в `pult/web/vendor/README.md`.

### Оболочка (фаза 3)

```
cd pult/shell
npm ci                                     поставить Electron (точной версией)
node node_modules/electron/install.js      ДОКАЧАТЬ двоичник Electron, если его нет
npm start                                  запустить оболочку
```

Из корня репозитория то же одной строкой: `npm --prefix pult run shell`.

**Про вторую команду — это не перестраховка.** На этой машине `npm install` положил только
пакет-обёртку: каталога `node_modules/electron/dist` и файла `path.txt` не появилось,
`postinstall` промолчал при `ignore-scripts: false`. Двоичник — 367 МБ, и без него `electron .`
не запускается с невнятной ошибкой. Проверить просто: `path.txt` и каталог `dist` обязаны быть.

**Нужны ОБА рантайма, и это не избыточность.** Electron 28 или новее — потому что раньше
главный процесс не умеет ESM, а весь пульт написан модулями. **Системный Node 18 или новее —
рядом с ним**, потому что демон поднимается ОТДЕЛЬНЫМ процессом системного Node, а не тем,
что внутри Electron: у того другой ABI, под ним нативный псевдотерминал не грузится,
и терминал переставал бы подниматься МОЛЧА — демон при этом стартует и страница работает.
Не нашёлся системный Node — оболочка отказывает явно и окна не открывает; указать его можно
переменной окружения `CCKIT_PULT_NODE` (абсолютным путём).

**Платформы:** Windows и macOS (x64 и arm64). Linux в фазе 2 не поддерживается: готовых сборок
псевдотерминала под него у апстрима нет ни в одной версии, а сборка на месте потребовала бы
компилятора у пользователя — это отменяет свойство «скачал и запустил». Решение человека
от 01.09.2026 с причиной, а не забывчивость.

## Маршруты

| Маршрут | Что отдаёт |
|---|---|
| `GET /health` | `{ ok, pult, node }` — состояние самого демона; по этим полям оболочка распознаёт СВОЙ демон на порту |
| `GET /pending` | что прямо сейчас ждёт человека по всем проектам реестра: проект, задача, причина. **Лёгкий**: обхода отпечатка в нём нет и быть не должно (§2.8 контракта, пункт 6) |
| `GET /projects` | список проектов реестра: у каждого версия, сверка отпечатка, активная задача, гейт |
| `GET /projects/:id` | то же на один проект плюс полный список задач; `id` — восемь шестнадцатеричных знаков |
| `GET /projects/:id/tree` | содержимое ОДНОГО каталога (`?dir=`): вид, метка git, признаки игнорирования, записи и секрета |
| `GET /projects/:id/file` | содержимое одного файла (`?path=`) и токен его состояния; `?reveal=1` — отдать файл под образцом секрета |
| `GET /projects/:id/diff` | без `?path=` — список изменённого; с `?path=` — ОБЕ стороны сравнения одного файла |
| `POST /projects/:id/file` | сохранение файла со сверкой токена — **единственный метод записи** |
| `GET /` и `GET /<файл>` | страница рабочего места из `pult/web` (закрытый словарь расширений) |
| `UPGRADE /ws/pty` | сессия псевдотерминала — **второй вход в демон**, со своей сверкой происхождения |

**Методов записи у демона по-прежнему ОДИН** — сохранение файла со сверкой токена. Маршрута,
принимающего путь проекта из запроса, у демона нет и быть не должно: проект в реестр заводит
инструмент командной строки `pult/tools/registry-add.mjs`, которого оболочка запускает
подпроцессом по нажатию человека. Это решение по итогам аудита фазы 3: корень из реестра
служит границей ВСЕМ проверкам пути в демоне, значит тот, кто назначает корень, назначает
и границу.

Форма ответа целиком выписана в разделе 1.5 контракта вместе со списком отклонений
от макета. Коротко, что важно знать потребителю:

- **перечислимые поля** (`status`, `mode`, `class`, `stop_kind` задачи; `status` и `verify`
  гейта; вердикты ревью и аудита), **версия, идентификаторы и все времена** отдаются только
  как совпадение с закрытым словарём кита или с привязанной регуляркой. Не совпало — `null`
  и код отказа в `faults[]`, сырая строка из чужого файла наружу не идёт;
- **свободный текст** (`title` и `branch` задачи, строки журнала, сводка и чек-лист итога,
  имена упавших проверок, `name` и `path` проекта, пути в `diverged[]`) очищен
  от управляющих символов и обрезан по потолку, но **не экранирован**: `<`, `>` и `&` в нём
  живые, и экранировать их обязан потребитель;
- у каждого времени стоит пометка вида (`local-naive`, `utc-iso`, `clock`, `date`), и она
  означает, что значение прошло проверку привязанной регуляркой своего вида. Ставит пометку
  только `timeField()` в `pult/lib/fs-safe.mjs` — руками объект времени не собирает ни один
  модуль.

### Проверка происхождения — на ДВУХ входах, а не на одном

Входов в демон два, и это главное, что изменилось на фазе 2: обработчик обычного запроса
и событие `upgrade`. Маршрутизатор до второго не доходит, а за адресом вебсокета стоит оболочка
машины — пока проверка жила внутри обработчика запроса, вебсокет обходил её целиком. Живёт она
теперь в `pult/lib/origin.mjs` и зовётся первой строкой в обоих местах: `requestRefusal()`
в обработчике запроса, `upgradeRefusal()` — в обработчике апгрейда.

На каждом запросе, до маршрутизации и до любого обращения к диску, сверяется заголовок `Host`:
он обязан точно совпасть с одним из закрытого списка (`127.0.0.1:7331`, `localhost:7331`).
Заголовок `Sec-Fetch-Site`, если он есть, обязан быть `same-origin` или `none`. Иначе — 403
и тело без единого поля данных.

На апгрейде к ним добавляется `Origin` по тому же правилу «есть — обязан совпасть, нет —
проходит»: браузер шлёт его на рукопожатии всегда, консольный клиент не шлёт вовсе, и именно
браузер здесь угроза. Отказ на апгрейде — уничтожение сокета **без рукопожатия** и одно своё
машинное слово (`host`, `site`, `origin`) в stdout; присланный заголовок в лог не идёт никогда.

Привязка к петле границей для браузера **не является**: страница заводит домен, который
переезжает на `127.0.0.1`, после чего запрос к `http://evil.example:7331/projects` для
браузера однопроисхожденный, а отсутствие заголовков общего доступа между источниками ответ
не удерживает — они управляют чтением ответа чужим источником, здесь же источник для браузера
свой. Сам `Host` Node не проверяет никогда.

## Реестр

```
%APPDATA%\cckit\registry.json      Windows
<HOME>/.config/cckit/registry.json POSIX (с уважением к XDG_CONFIG_HOME)
```

Хранит **только** путь, имя и время последнего просмотра — ничего о содержимом проекта.
Версия, отпечаток, задачи и статусы вычитываются с диска на каждый запрос: кэш здесь был бы
вторым источником правды, то есть ровно той болезнью, от которой в ките завели отпечаток.

**С фазы 3 у записи есть новое состояние — «корень отвергнут» (`root_rejected`).** Не всякий
абсолютный путь годится корнем проекта: домашний каталог, каталоги данных приложений,
системные каталоги, корень диска, каталог мастер-копии набора и каталог самого реестра
отвергаются. Обращаться с этим состоянием надо ровно как с «путь пропал»: **запись остаётся
в файле**, показывается человеку с причиной, и удаление её — по-прежнему решение человека.
Демон при этом отказывается под таким корнем и читать, и писать: отказ `root_rejected` стоит
у читателя проекта, у всех маршрутов пути, у моста сессии и у лёгкого маршрута ожиданий.

Каталог создаётся с режимом `0700`, файл — `0600`; на Windows смена режима пропускается мягко.
Пропавший путь помечается недоступным, но **никогда** не удаляется автоматически: исчезнувший
каталог бывает отключённым диском.

Сетевые (UNC) пути отбиваются на входе — и в реестре, и в инструменте добавления. Обращение
к такому пути уходит в сеть к чужому хосту с попыткой аутентификации: это и зависание,
и утечка учётных данных.

## Почему каталог демона не едет в чужие проекты

`pult/` лежит рядом с китом, а не внутри него, и в белый список набора (`.claude/ship.list`)
не вписан. Состав мастер-копии определяют этот список и раскладка рабочих мест; каталога
демона нет ни там, ни там, поэтому ни установщик, ни команды разворачивания его не копируют.
Пульт распространяется отдельно — это отдельный продукт над набором, а не его часть.

## Три решения, которые выглядят странно, пока не знаешь причины

### Различение «кита нет» и «чужой кит» — наша эвристика

Признака «это наш кит» в самом ките не существует. Демон различает состояния так:

- `no_kit` — папки `.claude` нет или это не каталог;
- `foreign` — папка есть, но в ней нет ни файла версии, ни списка состава, ни каталога
  агентов. Чужая `.claude` с ручными настройками — законный случай, и путать её с испорченным
  китом нельзя;
- `legacy` — кит есть, но нет каталога задач, а в рабочих файлах лежат одиночные план, ревью
  или аудит: так выглядели копии до 1.10;
- `ok` — всё остальное.

Эвристика наша, в ките её нет, и она будет уточняться по мере встречи живых случаев.
Разбор — `readKit()` в `pult/read/kit.mjs`.

### Усечённый обход даёт `unknown`, а не число

У отпечатка два разных признака, и путать их нельзя: `truncated` — обрезка списка расхождений
по потолку, `scan_truncated` — **неполный обход**. Второй взводится любым пропуском: файл сверх
потолка, не обычный файл, исчерпанные потолки или бюджет, нечитаемый файл, неперечислимый
каталог, несостоявшийся `lstat`.

Одинаковые имена — только у одинаковых смыслов: у эталона неполный обход называется тем же
словом `scan_truncated`, а обрезка списка проектов на верхнем уровне ответа — `projects_truncated`.
Одно `truncated` на три разных смысла в одном ответе было бы миной под фазу 2.

Исчерпанный бюджет **останавливает обход**, а не только чтение: первое исчерпание взводит флаг
в `ctx.halt` (`pult/lib/fingerprint.mjs`), и проверка в `ctx.join()` гасит обход и вглубь,
и вширь. Иначе синхронный обход разросшегося дерева продолжался бы после того, как читать уже
нечего, и держал бы весь демон вместе с `/health`.

Взводят флаг трое, и одних потолков чтения мало: каталог не стоит ни файла, ни байта, поэтому
дерево из одних каталогов их не тратит вовсе. Кроме потолков чтения обход считает **каталоги**
(`MAX_DIRS`) и спрашивает **время** (`budget.tick()` в `ctx.join()` — единственное место, где
синхронный обход смотрит на часы). Замер: 18 000 пустых каталогов держали `/health` 2,3 с,
после правки — 118 мс и честный `unknown` с кодом «исчерпан бюджет».

При неполном обходе значение не выдаётся вовсе (`value: null`), список расхождений пуст,
вердикт — только `unknown`, а `reason` несёт код причины. `mismatch` из неполного состава
не делается **никогда**: отпечаток от неполного состава — не отпечаток, а ложная тревога
обесценивает главный сигнал так же надёжно, как молчание. Демон читает кит проекта, в котором
прямо сейчас работают хуки, а на Windows файл, открытый на запись, даёт `EBUSY`/`EPERM` —
одного такого файла хватило бы на ложное «кит подменён».

Цена размена названа честно: подготовленный проект может погасить **свою** сверку, упершись
в любой потолок обхода. Человек увидит `unknown` с кодом причины прямо в ответе — и это лучше,
чем `mismatch`, которому нельзя верить.

### У эталона свой бюджет

Эталон — мастер-копия набора в `<HOME>/.claude/agent-kit` — считается **первым на каждом
запросе и по собственному бюджету**, отдельному от сквозного бюджета проектов. Иначе проект,
просканированный раньше, выбирает сквозной бюджет целиком, эталон не считается, и
`verdict: unknown` получают **все** проекты ответа: сверку целостности кита погасил бы один
чужой каталог в реестре.

К пути эталона демон обращается в том же порядке, что и к путям проектов: сначала форма
(UNC отбрасывается без обращения к диску), затем асинхронная проба доступности в гонке
с таймаутом, и только потом синхронный обход. Домашний каталог на сетевом ресурсе —
перенаправленный профиль Windows, домашние каталоги по NFS — не выдумка, а зависший
системный вызов остановил бы цикл событий **до маршрутизации**, вместе с `/health`.
Разбор — `readReference()` в `pult/read/reference.mjs`.

## Почему алгоритм отпечатка скопирован и чем это стережётся

Демон **никогда** не импортирует и не запускает код читаемого проекта: кэш модулей
противоречит запрету кэширования, а исполнение кода из чужого каталога — прямая дыра
(в реестр добавляют клон чужого репозитория). Поэтому алгоритм перенесён в
`pult/lib/fingerprint.mjs` дословно, в область между маркерами `// >>> ORIGIN`
и `// <<< ORIGIN`, а каждое изменение помечено `// pult:guard` и снабжено строкой
`//= <оригинал>`.

Совпадение стережёт `node pult/tools/fingerprint-parity.mjs`: он читает оригинал как текст,
восстанавливает из копии исходные строки и сравнивает построчно, а заодно считает пометки
ограждений — их девять, и отклонение в **любую** сторону даёт отказ.

**Оговорка, без которой сторож понимается неправильно:** он стережёт **алгоритм**, а не
ограждения. Строки с пометкой он из сравнения выбрасывает, поэтому ослабленное изнутри
ограждение — скажем, проверка вложенности, которая всегда возвращает истину, — пройдёт и
сверку, и канарейку. Ограждения держатся канарейкой по числу пометок и глазами человека:
при правке копии их перечитывают целиком, а не построчно.

Копия огорожена строже оригинала намеренно. `fingerprint()` в
`.claude/hooks/kit-fingerprint.mjs` ходит по **своему** киту, для него это не уязвимость,
и правило 2 раздела OVERVIEW запрещает трогать кит задачей пульта.

## Границы и принятые риски

**1. Проверка происхождения — не украшение, а единственная граница против браузера.**
_Решение 2026-08-31, действует и на фазе 2._ Привязки к петле мало: браузер обходит её
переездом домена на `127.0.0.1`, и без сверки `Host` запрос к чужому имени станет
однопроисхожденным. **Обещанное сбылось: за этим же адресом теперь стоит терминал с доступом
к оболочке машины**, и та же проверка стала защитой оболочки, а не только списка проектов.
Отсюда же второе следствие фазы 2 — сверка обязана стоять на **обоих** входах, включая
событие `upgrade` (см. раздел о проверке происхождения выше).

**2. Отклонение от §5.4 контракта: авторизации нет и на фазе 2 — риск снят УСЛОВИЕМ,
а не реализацией.**
_Решение 2026-08-31, пересмотрено 01.09.2026._ Контракт требует пин-кода с первого дня.
Его нет: любой локальный процесс читает всё, что отдаёт API, а с фазы 2 — ещё и открывает
сессию с оболочкой машины. Прежняя формулировка звучала «условие снятия: до первой строки кода
фазы 2»; она **заменена** решением человека от 01.09.2026, закрывшим открытый вопрос 2
контракта.

Суть решения: **демон остаётся на петлевом адресе, локальная сеть не включается вовсе**, а пин-код,
телефон, PWA и канал через VPS уезжают в фазу 5 целиком. Довод — в смене модели угроз, а не
в осторожности вообще: на фазе 1 худшим исходом подмены DNS была утечка данных, с терминалом
за тем же адресом тот же вектор означает **выполнение произвольных команд**, и «сеть только
домашняя» такой ценой не окупается.

Держится это **кодом, а не комментарием**: `LAN` в `pult/config.mjs` остаётся `false`,
и при `LAN === true` демон **останавливает старт** с объяснением и кодом возврата 1 —
включение сети обязано требовать осознанной правки вместе с авторизацией, а не смены одной
буквы в константе. Проверено на копии вне репозитория — п. 9 протокола фазы 2
в `pult/ACCEPTANCE.md`.

Что риск снят условием, а не устранён, надо держать в голове: **защищает не проверка, а то,
что снаружи в этот адрес не попасть.** Сверка `Host` и `Origin` остаётся единственной границей
против браузера на этой же машине.

**Уточнение 02.09.2026 (фаза 3), чтобы довод не пережил свою правду.** От локального клиента
сверка происхождения не защищает **вовсе** и защищать не может: он и так открывает сессию
с оболочкой машины через `/ws/pty`, не спрашивая ни `Host`, ни `Origin`. Говорить «сверка
защищает от локального актора» неверно — защищает недоступность адреса снаружи. **В фазе 5
этот довод придётся пересчитать целиком:** там появляется пин-код и выход в сеть, адрес
перестаёт быть недоступным, и единственная сегодняшняя опора исчезает.

**3. Принятый риск: жёсткие ссылки и потоки NTFS.**
_Решение 2026-08-31, уточнено на фазе 2._ Жёсткая ссылка и альтернативный поток данных
(`file:stream`) внутри чужой `.claude` от обычного файла не отличаются: `lstat` показывает
обычный файл. Наружу через отпечаток уходит только хеш — это оракул подбора, а не чтение,
и на фазе 1 риск принят.

**На фазе 2 у того же риска появилась вторая сторона — запись**, и закрыта она не проверкой,
а стратегией: временный файл плюс переименование не трогает исходный inode (пункт 6 ниже).
Поток данных в имени (`.env::$DATA`) проходит мимо образца секрета при чтении, а при записи
не срабатывает: переименование в поток падает.

**4. Реестр лежит в профиле пользователя.**
_Решение 2026-08-31._ Это список абсолютных путей с именем пользователя. Каталог `0700`,
файл `0600`; **на Windows режим не ставится** — прав такого вида там нет, и смена режима
пропускается мягко. Защита файла на Windows целиком лежит на правах профиля.

**5. Принятый риск: обход проекта, укладывающегося в бюджет, держит цикл событий, —
и теперь он задевает ТЕРМИНАЛ.**
_Решение 2026-08-31, подтверждено на фазе 2._ Обход отпечатка синхронный, и потолки
ограничивают, сколько будет прочитано, а не время, на которое встанет цикл событий. Пока дерево
укладывается в бюджет, останов не взводится вовсе, и `/health` ждёт вместе со всеми: на стенде
из 7202 мелких файлов (читается 5000) `/projects` отвечает за 2123 мс, худший `/health`
в это время — 2078 мс. Замер ревьюера на живом демоне — п. 8б протокола фазы 1
в `pult/ACCEPTANCE.md`.

**Что изменилось на фазе 2:** за тем же циклом событий теперь стоит живой терминал, и на время
обхода он не двигается — обновление списка проектов подвешивает сессию человека.

**Условие снятия было «до регулярного опроса фазы 2», и оно НЕ НАСТУПИЛО: регулярного опроса
в фазе 2 нет намеренно** — список проектов обновляется кнопкой. Заводить опрос, не перенеся
обход, нельзя. Настоящее лечение (обход в рабочем потоке либо порциями с возвратом в цикл
событий) — смена решения, а не правка потолков, и потому отдельное решение человека, а не
остаток фазы 2.

**6. Гарантия «в набор не пишем» стала ПРОВЕРОЧНОЙ, а не структурной.**
_Фаза 2._ Раньше её держало отсутствие методов записи; теперь её держит единственный шлюз
`resolveTarget()` в `pult/lib/fs-safe.mjs`, через который обязана проходить каждая запись.
Ослабление любой из его проверок открывает запись в кит, и снаружи это невидимо. Порядок
проверок и есть гарантия:

1. строки пригодны к обращению и не сетевые;
2. корень канонизируется `realpath` один раз, и дальше канонизированное сравнивается только
   с канонизированным;
3. режим записи: у проекта нет папки `.claude` — отказ `write_no_kit` **до** остальных проверок;
4. цель лежит внутри канонизированного корня;
5. оба режима: цель не внутри служебной папки `.git` ни на каком уровне;
6. режим записи: цель не внутри папки набора (обе базы) и не под образцом имени секрета;
7. `realpath` каталога-**родителя** и **повторная** проверка всех трёх условий по вернувшемуся
   пути — симлинк на родителя проверкой самой цели не ловится, а на Windows той же проверкой
   снимаются короткие имена вида `CLAUD~1`;
8. существующая цель обязана быть обычным файлом;
9. размер присланного текста в пределах потолка.

Дальше работа идёт **по разрешённому пути**, а не по присланной строке: иначе между проверкой
и записью родитель подменяется симлинком и проверка становится совещательной.

**Чего проверкой не закрыть, и это честно:** жёсткую ссылку внутри проекта на файл снаружи
`lstat` показывает обычным файлом, а родитель у неё честно внутри корня. Её отбивает не
проверка, а **стратегия записи** — временный файл в том же каталоге плюс переименование:
исходный inode при этом не трогается. Запись «на месте» здесь запрещена явно.

Меряет всё это `pult/tools/write-scope-check.mjs` (по проекту целиком, с раздельными
ожиданиями внутри и вне `.claude`); прежний `pult/tools/no-write-check.mjs` остаётся верным
по своей узкой формулировке и **недостаточным** — про запись за пределы выбранного файла он
не говорит ничего.

**7. Закрыты на запись ТРИ вещи, всё остальное в проекте открыто по замыслу.**
_Фаза 2._ Отказывает запись в: папку набора (`write_into_kit`), служебную папку `.git`
на любом уровне (`git_dir_closed`) и файлы под образцами секретов (`write_into_secret`);
отдельно закрыт **весь** проект, у которого нет папки `.claude` (`write_no_kit`). План фазы
называл закрытым только набор — `.git` и секреты добавлены находками ревью и решением
человека, и это **расширение шага 3**, а не самодеятельность (отклонение записано в §2.8
контракта).

Всё прочее в проекте пишется, и это **функция, а не дыра**: `.git/hooks/*` (лежат внутри
`.git` и потому закрыты), `package.json` со сценариями, `.gitattributes` и каталог самого
пульта, если он заведён в реестре, — пути исполнения. Клиент здесь человек, который и так
правит эти файлы редактором; пульт не притворяется песочницей.

**8. Окружений подпроцесса ДВА, и слить их обратно нельзя.**
_Фаза 2._ `gitEnv()` — служебное окружение git: строится **явно из белого списка** и ужесточает
git (`GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` в несуществующий
путь). `sessionEnv()` — сессионное окружение терминала: **наследует** окружение демона минус
закрытый список — `CCKIT_*` (в первую очередь `CCKIT_GATE`, которую `decide()`
в `.claude/hooks/gate.mjs` читает первой строкой), `NODE_OPTIONS`, `GIT_DIR`, `GIT_WORK_TREE`,
`GIT_INDEX_FILE`.

Почему именно два. Общее окружение ломает `git commit` в терминале («Author identity unknown»:
белый список отрезает `user.name` и `credential.helper`), а лечат такую поломку наследованием
целиком — и тогда пульт молча раздаёт `CCKIT_GATE=off` всем сессиям, то есть снимает остановку
«СТОП» вопреки правилу 3 раздела OVERVIEW. Проверено живьём в обе стороны: демон, поднятый
с `CCKIT_GATE=off`, отдаёт в сессию `undefined` и ноль переменных с приставкой `CCKIT`, а
`git commit --dry-run` в той же сессии на автора не жалуется (пп. 1 и 3 протокола фазы 2
в `pult/ACCEPTANCE.md`).

**9. Команда подпроцесса всегда абсолютная и разрешается по `PATH`, а не по рабочему каталогу.**
_Фаза 2._ Рабочий каталог здесь — корень чужого проекта из реестра, а libuv на Windows
разрешает имя без разделителя, просматривая `cwd` **раньше** `PATH`: подложенный в клон
`git.exe` выполнился бы вместо системного, и триггером стало бы простое открытие проекта
в левой колонке. Единая дверь — `resolveCommand()` в `pult/lib/fs-safe.mjs`: имя в абсолютный
путь, элементы `PATH`, не являющиеся абсолютными путями, **пропускаются**, не разрешилось —
код отказа, а не попытка запустить имя.

Командный файл (`.cmd`, `.bat`) поднимается через `%ComSpec%` **по абсолютному пути**
и с ключами `/d /s /c`, а командная строка собирается нами из констант и разрешённого пути,
с нашими кавычками (`cmdForm()` там же). Форма запуска берётся потребителями **целиком**
и по частям не пересобирается.

**Оговорка, которую нельзя потерять:** `NoDefaultCurrentDirectoryInExePath=1` прикрывает поиск,
который делает **сам ребёнок**, а наш запуск libuv разрешает сам — этой переменной он
не спрашивает. Единственная защита здесь — абсолютный путь.

**10. Чужой репозиторий в реестре — АКТ ДОВЕРИЯ.**
_Фаза 2._ `.git/config`, приехавший копией каталога (клон такой конфиг не переносит, копия
переносит), и `.gitattributes` из дерева умеют исполнять команды:

- `core.fsmonitor` и `core.hooksPath` — при первом же запросе состояния; закрыты общей
  приставкой аргументов;
- `diff.external` и `textconv` в паре с `diff=x` в `.gitattributes` — при открытии вкладки
  диффов; закрыты приставкой подкоманды `--no-ext-diff --no-textconv`, и приставляется она
  в единственном пусковом примитиве по имени подкоманды, а не переписывается у каждого вызова;
- `filter.<drv>.clean` в паре с `filter=` в `.gitattributes` — исполняется уже на `git status`,
  и **ключа «не запускать фильтры» у git нет**. Этот вектор не закрывается ничем.

Лечение одно и оно организационное: **не заводить в реестр репозиторий, которому не доверяешь.**

**11. Секреты проекта по умолчанию не отдаются — это умолчание, а не стена.**
_Фаза 2._ Файлы под теми же пятью образцами, что стоят в `permissions.deny` набора (`.env`,
`.env.*`, `*.pem`, `*.key`), помечаются в дереве, не отдаются читателем без явного признака
`reveal`, исключаются из списка диффа и из обеих сторон сравнения, а на запись закрыты
**насовсем** — парного `reveal` ключа у сохранения нет. Асимметрия намеренная: показ обратим
и оставляет след строкой в stdout, перезапись `.env` не лечится ничем.

Стеной это не является и притворяться ею не должно: локальному процессу умолчание не мешает,
тот же файл читается обычным `cat`. Смысл умолчания в том, что осознанное действие **видно**,
а неосознанного не происходит.

**12. Буфер сессии — осознанное исключение из правила «ничего не кэшировать».**
_Фаза 2._ Правило 1.3 контракта запрещает хранить между запросами **факты о проекте**; буфер
хранит **вывод живого процесса**. Граница исключения такая: ни версия, ни отпечаток, ни задачи,
ни статусы в нём не оседают, объём ограничен кольцом, и смерть сессии он не переживает —
вместе с процессом уходит и он. Нужен он ровно для одного: вернувшийся клиент получает
последний экран, иначе таймер пяти минут держал бы процесс без всякой пользы.

**13. Целостность поставки — часть границы, а не бухгалтерия.**
_Фаза 2._ Привезённые сборки (`monaco-editor`, `xterm.js`) **исполняются на странице,
за которой стоит терминал**: их подмена равна подмене терминала. Поэтому опись состава,
происхождения и sha256 лежит в `pult/web/vendor/README.md`, версии зависимостей точные,
а файл блокировки коммитится и ставится через `npm ci`.

Про нативный модуль сказано, чем целостность проверена и чем нет: готовая сборка
псевдотерминала лежит **внутри** архива пакета, значит покрыта полем `integrity` файла
блокировки, и это подтверждено разбором пакета. Не покрыты доверием **первая** запись
блокировки и честность апстрима — обе стороны названы в описи.

**14. Корень проекта в реестре больше НЕ «любой абсолютный путь».**
_Решение 02.09.2026, фаза 3._ Корень из реестра служит границей **всем** проверкам пути
в демоне: `resolveTarget()` в `pult/lib/fs-safe.mjs` честно меряет вложенность в назначенный
ему корень. Значит тот, кто выбирает корень, выбирает и границу. Корень, равный домашнему
каталогу, отдавал бы через дерево и файл весь поддерев, **признаком `reveal` — файлы под
образцами секретов и переписку Claude Code в `<HOME>/.claude`**, методом сохранения доставал
бы до автозагрузки и профиля оболочки, а сессией терминала — до оболочки машины в доме.
Это чтение секретов машины, а не одного проекта.

Что отвергается и с какой пометкой:

- **точно, только сам каталог** — домашний каталог, каталог, в котором лежат домашние каталоги
  (`C:\Users`, `/home`, `/Users`), каталоги данных приложений (`APPDATA`, `LOCALAPPDATA`),
  корень диска и корень файловой системы;
- **вместе со всем содержимым** — каталог набора в домашнем (`~/.claude`), системные каталоги
  Windows и типовые системные каталоги POSIX, каталог реестра самого пульта.

**Список ЧЁРНЫЙ, и это осознанно.** Он ловит правдоподобную ошибку человека в диалоге выбора
папки, а не нападающего: у локального нападающего и так есть сессия с оболочкой машины через
`/ws/pty`. Забытая строка здесь не открывает ничего нового — остаётся сегодняшнее поведение;
этим он и отличается от `.claude/ship.list`, где забытая строка означала бы уехавший в чужой
проект файл. **Это лежачий полицейский, а не граница** — тем же словом, каким описаны правила
`deny` на git в `.claude/CLAUDE.md`.

**Решение человека 02.09.2026 по каталогам данных приложений — довод целиком.** Они сверяются
**точно**, а не вместе с содержимым. Довод: запись под такими корнями и так требует папки
`.claude` в самом корне, а её нет ни у временного каталога, ни у папки автозагрузки — отказ
`write_no_kit` в шлюзе стоит независимо от этого списка; правдоподобную ошибку мышью («выбрал
каталог данных приложений целиком») точная сверка ловит по-прежнему. Вариант «исключить
временный каталог из запрета» отвергнут: **исключение внутри чёрного списка хуже более
короткого списка** — то же рассуждение, что записано в шапке `.claude/ship.list`.
**Следствие называется вслух: подкаталоги этих каталогов снова можно завести проектом**, и это
принятое решение, а не недосмотр. В системном временном каталоге разворачивают свои стенды
`pult/tools/page-check.mjs` и `pult/tools/write-scope-check.mjs`, и оба заводят их в реестр
прогона.

**Чего этот список не закрывает и никогда не закрывал: ЧТЕНИЯ.** Довод про `write_no_kit` верен
только для записи. После перевода каталогов данных приложений на точную сверку подкаталоги
этих каталогов можно завести проектом, и чтение под ними закрывает только то, что человек сам
такой корень не заводит: маршрута записи в реестр у демона нет, добавляет проект человек.

**15. Сверка корня строковая и синхронная — известная ГРАНИЦА УТВЕРЖДЕНИЯ, а не долг.**
_Решение 02.09.2026, фаза 3._ Тот же каталог, вписанный в реестр руками коротким именем
Windows (`MANUKY~1`) или через точку соединения, под запрет не подводится: сравнение идёт
по строке. Путь, прошедший через `pult/tools/registry-add.mjs`, этим не задет — инструмент
делает `resolve` плюс `realpath` **до** записи, и в файл ложится каноническая длинная форма.
Ограничение касается записей, вписанных в файл реестра руками. Формулируется как названная
граница утверждения; изменение — отдельное решение.

**16. Писателей у файла реестра ТРОЕ, и межпроцессной атомарности нет.**
_Решение 02.09.2026, фаза 3; дополнено 03.09.2026, фаза 4._ Пишут `addProject()` (инструмент
реестра), `touchProject()` (сам демон, отметкой просмотра на каждом запросе одного проекта)
и — с фазы 4 — тот же `addProject()`, вызванный **раскладчиком** в конце удавшейся раскладки
(`deploy()` в `pult/deploy/deploy.mjs`). Третий писатель ничего не меняет в модели гонки:
дверь та же и проверка корня та же, — но «писателей двое» перестало быть правдой. Формулировка «писатель один» неверна
и в документах пульта не употребляется. Окно потери у демона миллисекундное и внутри демона
разведено счётчиком обходов: синхронный обход отпечатка лежит в `collect()` и отрабатывает
РАНЬШЕ, а `touchProject()` перечитывает реестр непосредственно перед записью. Требование
«не переносить чтение выше по потоку» живёт комментарием рядом с кодом — машинного сторожа
у него нет и быть не может. **Остаток назван: проект, добавленный инструментом ровно между
чтением и записью отметки, будет затёрт без следа.** Лечится файлом-замком; замок в эту фазу
не взят намеренно — он вводит своё состояние на диске (снятие зависшего, возраст, поведение
при падении процесса), а цена промаха здесь «нажать „Добавить проект“ второй раз».

**17. Оболочка поднимает демон СИСТЕМНЫМ Node, и рантайм Electron для этого не годится.**
_Решение 02.09.2026, фаза 3._ Внутри Electron путь исполняемого файла процесса — это бинарник
Electron, а переменная запуска Electron в режиме Node даёт Node с **ABI Electron**. Под ним
демон СТАРТУЕТ, страница живая, HTTP отвечает — а `loadPty()` в `pult/lib/pty.mjs` ловит
исключение загрузки нативного модуля и возвращает пустоту: **терминал молча перестаёт
подниматься**, и человек ищет поломку в терминале, а не в способе запуска. Поэтому рантайм
ищется единой дверью `resolveCommand()`, версия спрашивается запуском с таймаутом и потолком
вывода, не нашёлся — явный отказ с человекочитаемой причиной и **без открытия окна**.

**Честная оговорка про дверь:** она закрывает поиск исполняемого файла по рабочему каталогу
и требует абсолютного пути, но **не закрывает подмену самого файла в каталоге из переменной
путей**. Тот, кто может записать в каталог `PATH`, получает выполнение и без нас. Обещать
здесь больше этого нельзя.

**18. Владение демоном живёт в памяти оболочки, а проба здоровья не защищает от подставленного
ответчика.**
_Решение 02.09.2026, фаза 3._ Файла с номером процесса нет намеренно: он пережил бы падение
оболочки, и следующий запуск гасил бы по нему чужое дерево — номера переиспользуются. Правило
простое: подняли сами — гасим (и при выходе, и при любом отказе, случившемся уже после
запуска); распознали чужой или свой, но поднятый снаружи — не трогаем никогда. Номер процесса
помнится, пока ребёнок жив, и снимается по событию его завершения.

**Формулировка про пробу держится точной:** три поля ответа (`ok`, имя пульта, разбираемая
версия) подделываются тривиально, поэтому проба распознаёт **чужую службу и старый демон**,
но защитой от намеренной подмены не является. Потери от этого нет: у того, кто занял петлевой
порт, и так есть выполнение кода на машине. Ценность пробы в другом — окно с мостом в главный
процесс и системным диалогом не открывается над **чужой** страницей.

**19. Опрос по расписанию появился — и почему это не нарушает условие §2.8 пункта 6.**
_Решение 02.09.2026, фаза 3._ Условие звучало так: заводить регулярный опрос, не перенеся
синхронный обход отпечатка в рабочий поток, нельзя — за тем же циклом событий стоит живая
сессия человека, а обход измерялся секундами. Условие соблюдено **не переносом обхода,
а маршрутом, в котором его нет**: `readPending()` (`pult/read/pending.mjs`) читает состояние
задач и приёмки и не зовёт ни читателя состояния набора, ни обхода дерева, ни списка состава,
ни отчёта приёмки. Замер при живой сессии — 15–18 мс на вызов против примерно двух секунд
у полного обхода. Интервал опроса — минута: задача ждёт человека часами, а не секундами.
У маршрута свой бюджет и свой счётчик одновременности (два), потому что звать его может любой
локальный клиент, а не только наш опрос.

**20. Уведомления на Windows у НЕУПАКОВАННОГО приложения могут не показываться.**
_Решение 02.09.2026, фаза 3._ Идентификатор приложения выставляется при старте в любом случае,
но упаковки в фазе 3 нет, и это известный случай: система может проглотить уведомление молча,
что неотличимо от «ничего не ждёт». Запасной путь — подсказка иконки трея, она обновляется
каждый круг опроса. Отдельно: чужой свободный текст (имя проекта, заголовок задачи) идёт
в уведомление **очищенным и экранированным** — на Windows текст собирается системой как XML,
и угловая скобка или амперсанд дают тихо не показанное уведомление. Остаток назван: если
платформенный слой экранирует ещё раз, человек увидит `&amp;` вместо `&` — косметика, и она
дешевле непоказанного уведомления.

**21. Страница в окне Electron — обычный удалённый источник.**
_Решение 02.09.2026, фаза 3._ Одна дыра страницы иначе масштабируется на всю машину, поэтому
границы окна держат ту же линию, что сверка происхождения на демоне: изоляция контекстов
включена, доступ к платформе выключен, песочница включена, `webSecurity` остаётся включённым,
`webviewTag` выключен, перехватываются не только переход, но и переадресация, и переход
во вложенном кадре, открытие новых окон запрещено целиком, права отклоняются обоими
обработчиками, внешние ссылки открываются только адресом из констант.

**Мост не принимает пути ни в каком виде, и на этом держится снятая находка круга 1 аудита.**
Метод «завести проект» не имеет и не получит параметра пути — ни целиком, ни частью, ни
подсказкой начального каталога; отдельного метода «показать диалог» нет. Единственный источник
пути — системный диалог главного процесса, и обработчик не читает из сообщения страницы
ничего. Один необязательный аргумент вернул бы ту находку целиком, и больше её не ловит ничто.

**22. Уборка за брошенным ребёнком — НАЗВАННАЯ ГРАНИЦА УТВЕРЖДЕНИЯ, а не гарантия.**
_Решение 02.09.2026, фаза 3._ Оболочка (`pult/shell/`) поднимает демон отдельным процессом
системного Node и гасит его сама: и при выходе, и при любом отказе, случившемся уже после
запуска (`failAfterSpawn()` в `pult/shell/daemon.mjs`). Правило простое: подняла — гасит;
распознала чужого — не трогает никогда.

**Чего это НЕ обещает.** Оболочка, снятая жёстко, до останова не доходит вовсе, и тогда судьба
ребёнка — дело платформы, а не наше. На Windows брошенный ребёнок уходит вместе с родителем;
это ПОВЕДЕНИЕ ПЛАТФОРМЫ, оно проверено двумя независимыми пробами и **в коде на него никто
не опирается**. **На POSIX такого поведения нет: ребёнок переживает родителя** и умирает лишь
случайно — на первой записи в разорванную трубу. **POSIX в фазе 3 не проверялся вовсе**:
целевая платформа §3.3 контракта — Windows, готовых сборок псевдотерминала под Linux
у апстрима нет, macOS проверяется по остаточному принципу.

Худший исход назван вслух: брошенный демон висит на порту, не отвечая, и следующий запуск
оболочки не поднимется никогда — сообщение «Пульт не запустился» про свой же оставленный
процесс ничего не скажет. Файла с номером процесса, по которому такого сироту можно было бы
найти, нет намеренно: он пережил бы падение оболочки, и следующий запуск гасил бы по нему
чужое дерево (решение 7 плана фазы 3).

**23. Отложенный дефект: гонка выбора проекта во вкладке диффов.**
_Найдено и НЕ вылечено 02.09.2026, фаза 3, решение человека._ Открыть вкладку диффов,
не дождавшись конца выбора проекта, — `diff.load()` успевает наполнить список файлов,
а завершающий `diff.reset()` из `selectProject()` (`pult/web/app.mjs`) обнуляет идентификатор
проекта уже после этого. Список на экране есть, а клик по файлу уходит на `/projects//diff`
и даёт «отказ демона: неизвестно».

**Воспроизведено**, а не выведено из чтения: проверка 4 в `pult/tools/page-check.mjs` ловила
именно это, пока в неё не добавили ожидание конца выбора проекта.

**Чем лечится:** сбрасывать вкладку диффов в начале `selectProject()`, а не в конце, либо
считать поколение выбора и отбрасывать устаревший сброс — тем же приёмом, каким `open()`
в `pult/web/editor.mjs` отбрасывает ответ на устаревший запрос.

**Почему отложено:** цена мала — путаное сообщение на быстром клике, лечится повторным
кликом, ни данных, ни прав не задевает; правка лежала бы в файле, закрытом другой частью
задачи. Записано здесь и в §3.4 контракта **именно потому**, что запись в папке задачи
не переживёт задачу: `.claude/tasks/` выведен из-под git целиком.

**24. Окно прячется в значок ТОЛЬКО когда есть куда возвращаться, и Windows может значок
спрятать.**
_Найдено человеком и исправлено 02.09.2026, фаза 3._ Первая редакция прятала окно в трей
безусловно, а завершал приложение только пункт меню значка. Связка «единственный выход — трей»
и была дефектом: значка в области уведомлений человек не увидел, окно спряталось, приложение
осталось жить невидимым, и снять его можно было только диспетчером задач.

**Что теперь:** `createTray()` возвращает отчёт, и закрытие окна **прячет его только при
годном значке**; трей негоден — закрытие завершает приложение. При первом сворачивании
человек получает уведомление, куда именно ушло окно. Второй запуск пульта по-прежнему
показывает уже открытое окно — это штатный способ вернуть спрятанное.

**Названная граница утверждения, которую код закрыть не может:** «значок не построился»
и «значок построился, но Windows 11 спрятала его в переполнение (стрелка «Отображать скрытые
значки» у часов)» — разные вещи, и вторую система не сообщает никак. Проверено замером:
картинка строится, не пуста, 32×32, `new Tray` не бросает — то есть на стороне пульта значок
есть. Если его не видно, он в переполнении: вытащите его мышью на панель либо включите
в «Параметры → Персонализация → Панель задач → Другие значки в области уведомлений».

**25. Остановка демона видна человеку сразу, а не по симптомам.**
_Найдено человеком и исправлено 02.09.2026, фаза 3._ Демон остановился — страница продолжала
показывать зелёную точку и «демон 0.3.0», потому что здоровье перечитывалось только на старте
и по кнопке «Обновить». Каждый виджет при этом говорил своё: дерево — «каталог не прочитан»,
карточка — прочерки. Человек прочитал это как поломку дерева при переключении проектов.

Лечится в одном месте — в общей двери запросов страницы: обрыв переводит полосу состояния
в «демон не отвечает», первый удавшийся запрос возвращает её обратно. Со стороны оболочки
добавлено второе: уход СВОЕГО демона без нашей команды больше не остаётся строкой в журнале,
а доходит до человека уведомлением.

**26. Пишущая раскладка живёт ОТДЕЛЬНЫМ каталогом, и это правило каталожное.**
_Решение 03.09.2026, фаза 4._ Всё, что пишет в чужой проект, лежит в `pult/deploy/**`, и ни один
его модуль не входит в граф импортов демона. Чистое — профили, правило ядра и формула отпечатка
по составу — живёт в `pult/lib/profiles.mjs`, рядом с копией алгоритма отпечатка и по той же
причине: эти функции зовут читатели демона. Положи мы чистое в каталог раскладки — каталог
вошёл бы в граф демона, и собственная проверка правила стала бы красной, а самым дешёвым
выходом из красной проверки было бы её ослабление.

Правило проверяется транзитивным обходом импортов от точки входа демона (проверка 2
в `pult/tools/deploy-check.mjs`). **Граница названа: обход видит СТАТИЧЕСКУЮ форму импорта.**
Динамический импорт и построенный требователь проходят мимо него.

**27. Атомарности «либо всё дерево, либо ничего» нет; страховка — резервная копия.**
_Решение 03.09.2026, фаза 4._ Раскладка копирует файлы по одному, и обрыв посередине оставляет
проект в промежуточном состоянии. Вместо атомарности — копия папки набора в соседнюю
`.claude.backup-<дата>`, сделанная ДО первого байта и сверенная по числу файлов, объёму
и числу пропущенного. **Непустой список пропущенного ОСТАНАВЛИВАЕТ раскладку**, а не
предупреждает: копия без символических ссылок исходного дерева откатом не является,
и «сошлось» означало бы «сошлось по тому, что мы согласились считать». Неполную копию
раскладчик не удаляет — путь называется, уборка на человеке.

**28. Слияние с чужим файлом настроек: своя группа, явный порядок, владение как объединение.**
_Решение 03.09.2026, фаза 4._ Наши строки прав дописываются, наши хуки ставятся ОТДЕЛЬНЫМ
элементом массива события, чужая группа не правится вовсе. Внутри нашей группы порядок задан
кодом, а не унаследован из мастер-копии: начало сессии первым, баннер вторым — хуки одной
группы делят общий бюджет времени, и при обратном порядке запись границы сессии гибнет МОЛЧА.

Строка, уже бывшая в чужом файле, во владение не записывается никогда; владение —
**объединение** прежнего и добавленного, иначе повторная раскладка сузила бы его, и снос
оставил бы наши строки в чужом файле навсегда. При сносе группы снимаются ТОЛЬКО при
дословном совпадении, а сравнение в слиянии идёт по каноническому виду: порядок ключей после
любого форматтера меняется, и строгая сверка задваивала бы нашу группу.

**29. Снос идёт по НАШЕЙ записи, только из папки набора, и память проекта защищена независимо от неё.**
_Решение 03.09.2026, фаза 4._ Удаляет только тот, кто клал: список положенного из
`.claude/.cckit-deploy.json`. Записи нет или она не разобралась — отказ целиком, а не догадка.
Реестр установленных файлов набора здесь не читается вовсе: `owned()` в
`.claude/hooks/write-manifest.mjs` считает нашим всё, чьё ИМЯ есть в мастер-копии, и снос по нему
унёс бы чужой хук, который additive-копия намеренно не тронула.

Память проекта — папки задач, журнал событий и история — не удаляется НИКОГДА, что бы
ни лежало в записи: запрет стоит в шлюзе и от записи не зависит. Под этим есть машинная
опора: проверка 1 в `pult/tools/deploy-check.mjs` утверждает, что ни один путь памяти
не появляется в списке положенного, — сегодня это верно по построению, и утверждение стережёт
БУДУЩУЮ правку.

**30. Исполняется только свой хук с совпавшим хешем; безопасность несёт СВЕРКА ХЕША.**
_Решение 03.09.2026, фаза 4._ После копирования раскладчик запускает два хука набора из самого
проекта. Условий два: хук обязан быть в списке положенного ЭТОГО прогона и его хеш обязан
совпасть с файлом мастер-копии. Безопасность несёт второе: исполнение файла, байт в байт
равного эталону, и есть исполнение нашего файла. **Снимать правками можно любое из двух,
кроме сверки хеша.**

**Названная граница: окно между сверкой и запуском не закрывается и закрыто быть не может** —
запуск идёт по пути, а не по открытому дескриптору. Остаток мал: чтобы в него попасть, нужен
процесс с правом записи в каталог хуков проекта, а такой процесс и так получает исполнение
через обычную регистрацию хуков.

**31. Сверка идёт по составу профиля; ядро сверяется ПРОТИВ ЭТАЛОНА.**
_Решение человека 02.09.2026, реализовано 03.09.2026, фаза 4._ Эталон считается не целиком,
а по путям профиля: проект с неполным профилем полному эталону не равен никогда, и сторож,
кричащий всегда, обесценивает сигнал так же надёжно, как молчащий. У совпадения по составу
своё слово вердикта — `match_preset`, и при нём **полного значения у проекта не существует
вовсе**: список состава едет в проект целиком, а исключённых каталогов в нём нет, поэтому обход
честно взводит признак усечения. Карточка показывает значение ПО СОСТАВУ.

Условие ядра звучит дословно: **каждый путь ядра эталона (эталон ∩ профиль) присутствует
в карте проекта, и его хеш равен эталонному**. Требования быть в списке положенного НЕТ,
и причина важнее удобства: список положенного — это фактически записанное ТЕМ прогоном,
а на главном сценарии §4.2 (раскладка туда, где набор уже стоит) всё ядро пропускается
additive-копией. Такое условие давало бы «ядро не наше» НАВСЕГДА у каждого такого проекта,
причём без возможности назвать причину. Членство в положенном безопасности не несёт вовсе:
перечень ядра приходит СНАРУЖИ, из эталона, и подделать его записью проекта нельзя.

**Файл настроек отпечатком не сверяется никогда** — он в списке пропускаемых у самого
алгоритма набора. Это существующая граница набора, а не решение этой фазы: подмена внутри
служебного ключа владения не видна ни сверке, ни панели настроек — только глазам.

**32. Раскладчик работает ВНЕ модели прав Claude Code.**
_Решение 03.09.2026, фаза 4._ Это обычная команда, запущенная оболочкой: правила `permissions`
из `settings.json` на неё не распространяются никак. Отсюда маркерный отказ на репозиторий
самого набора — в корне одновременно `install.ps1` и `install.sh` либо первые строки
`.claude/CLAUDE.md` называют Claude Agent Kit. Без него инструмент переписал бы здесь
`.claude/settings.json`, закрытый правилами `deny` НАМЕРЕННО, и правами это не ловится.

**33. Мост принимает параметры, и всё, что меняет состояние, требует подтверждения.**
_Решение 03.09.2026, фаза 4._ До фазы 4 ни одна функция моста не принимала ничего. Теперь
нужны выбор проекта и команды, поэтому параметром бывает только идентификатор известной формы
или слово из закрытого словаря, и ни один параметр не участвует в построении пути. Мост живёт
в одном процессе со страницей, поэтому его проверки — удобство, а границей они становятся
в главном процессе, где повторяются. Всё, что пишет на диск проекта — раскладка, снос, четыре
статуса задачи и закрытие, — требует СИСТЕМНОГО ОКНА подтверждения.

**34. Выбранный путь возвращается на экран мастера — держится НАПРАВЛЕНИЕ.**
_Решение 03.09.2026, фаза 4, проверено аудитом фазы._ §4.2 требует показать человеку, куда
ставим и где будет копия, поэтому путь уезжает на страницу в отчёте осмотра. Находку круга 1
аудита фазы 3 это не возвращает: она была про то, что страница не может НАЗНАЧИТЬ корень.
Источников пути по-прежнему два, и оба вне страницы: системный диалог главного процесса
и реестр по идентификатору.

**35. Ключ подмены источника заперт во временный каталог.**
_Решение 03.09.2026, фаза 4._ `--from` у инструмента раскладки принимается ТОЛЬКО когда цель
лежит внутри временного каталога системы. Причина: сверка хеша хуков идёт против той же
подменённой копии, значит без запрета ключ раскладывал бы произвольное дерево в живой проект
и исполнял его хуки как свои. Довод «оболочка его не передаёт» — утверждение про оболочку,
а не про того, кто может позвать оболочку машины.

**36. Чужие файлы правятся БАЙТ В БАЙТ; окончания строк не «чинятся».**
_Решение 03.09.2026, фаза 4._ Файл игнорирования читается байтами, вставка идёт по байтовому
смещению теми же окончаниями строк, что преобладают в файле, а кодировка и отсутствие
завершающего перевода строки сохраняются. Разбор по одному виду перевода и склейка другим
раздували бы дифф чужого репозитория на весь файл, а правим мы одну строку.

**37. Известный остаток: повторная раскладка вернёт строку игнорирования, которую человек убрал ОСОЗНАННО.**
_Названо 03.09.2026, фаза 4, НЕ закрыто._ Правило «нет точного вхождения — добавляем»
не отличает «мы ещё не добавляли» от «человек убрал намеренно», а убрать её — законное
действие: команда `/cckit_push-with-me` существует ровно затем, чтобы включить файлы набора
в репозиторий проекта, и заканчивается словами «сам не правь». Закрывается тем же приёмом,
что владение в файле настроек, и в эту фазу не взят. Направление отказа безопасное — мы
добавляем строку, а не убираем.

**38. Ответ на живой `[СТОП]` остаётся ручным, и критерий готовности фазы по нему ОТКРЫТ.**
_Решение человека 02.09.2026, фаза 4._ §4.5 сужен: пульт принимает `DONE.md` и запускает
команды набора, а ответ на живой стоп по-прежнему набирается в терминале пульта. Причина
не в лени: **места для ответа человека в наборе нет вовсе** — `cmdStop()` в
`.claude/hooks/task.mjs` пишет только вид стопа, — а имени события «человек ответил» нет
в белом списке `.claude/hooks/events.mjs`. Это отдельная задача НАБОРА, а не пульта.
Уведомление при этом ведёт на вкладку терминала и говорит, что делать; **сессия
не поднимается сама** — поднимать оболочку машины по внешнему событию нельзя.

## Кит обязан работать без пульта

Правило 2 раздела OVERVIEW: ни одна фаза не имеет права добавить в набор зависимость
от контроллера. **Ни фаза 1, ни фаза 2 не тронули в ките ни одного файла** — ни одного шага
плана с таким файлом не было ни там, ни там.

Проверяется так: остановить демон и убедиться, что конвейер отвечает как раньше —

```
node .claude/hooks/task.mjs list
node .claude/hooks/gate.mjs --dry
```

Обе команды работают при остановленном демоне и ничего о нём не знают. Протоколов в
`pult/ACCEPTANCE.md` ДВА, и здесь названы пункты из обоих: п. 6 протокола фазы 1 («кит обязан
работать без пульта») и п. 11 протокола фазы 2 («конвейер запускается из системной консоли»);
на фазе 2 проверка повторена с тем же исходом.

**Обратная сторона того же правила** — пульт не имеет права ослабить машинную приёмку набора.
Проверяется п. 3 протокола фазы 2: демон, поднятый человеком с `CCKIT_GATE=off`, в сессию
эту переменную не отдаёт.

## Чего эта проверка про пульт НЕ доказывает

Машинная приёмка набора (`CCKIT:VERIFY` в §2 `PROJECT_PROFILE.md`) **не покрывает `pult/**`
ни строкой**: её пять проверок — это два `node --check` по хукам набора, самопроверка
`check-syntax.mjs`, баннер и `bash -n install.sh`. Зелёный `VERIFY.json` о работоспособности
пульта не говорит **ничего**, и это не догадка: в ходе фазы 2 страница была нерабочей
(полотно сравнения схлопывалось в полосу высотой 5 пикселей) при зелёной приёмке.

Всё, что доказано про пульт, доказано протоколом `pult/ACCEPTANCE.md` и ручными прогонами
в нём. Завести проверки пульта в блок `CCKIT:VERIFY` — отдельное решение человека: блок
правится руками и подтверждается `verify.mjs --accept` из терминала.

## Что в этот каталог не входит

**Из фазы 3 не входит намеренно:** упаковка в дистрибутив (ни сборщика, ни исполняемого файла,
ни установщика, ни подписи, ни автообновления — пульт запускается из исходников) и автозапуск
самой оболочки при входе в систему. Вводка §3 контракта говорит об автозапуске демона — он
закрыт тем, что демон поднимает оболочка.

Раскладка кита в проект, профили, настройки проекта и запуск команд набора кнопками сделаны
фазой 4. **Ответ на живой `[СТОП]` через интерфейс в неё НЕ вошёл** — §4.5 сужен решением
человека, ответ по-прежнему набирается в терминале пульта, и критерий готовности фазы по нему
остаётся открытым (пункт 38 ниже). Сеть, пин-код, телефон, PWA и веб-уведомления —
фаза 5; константа доступа в локальную сеть выключена и **запирает старт демона**. Карта
памяти, дашборд с цифрами и сводный индекс — фаза 6.

Не входят и вещи помельче, названные отклонениями в §2.8 контракта: файловые операции в дереве
сверх создания и сохранения (переименовать, скопировать, перенести, перетащить извне), второй
канал с потоковым JSON, диаграмма Ганта по агентам, пометка «агент правит этот файл прямо
сейчас». Ограничение частоты запросов, кэш фактов о проекте и любой индекс — по-прежнему
не здесь и не сейчас.
